# 웹소설 메타데이터 수집기 구현 계획

## 현재 상태

- 프로젝트 문서와 작업 원칙 작성 완료
- DB 없는 FastAPI 골격 작성 완료
- 문피아 검색 및 상세 메타데이터 수집 구현 완료
- 네이버 시리즈와 카카오페이지 수집 및 세 플랫폼 병렬 검색 구현 완료
- 노벨피아 수집 및 네 플랫폼 병렬 검색 구현 완료
- 리디 공개 검색 JSON 수집 및 다섯 플랫폼 병렬 검색 구현 완료
- 전체 후보 중 한 작품을 선정하는 `/api/v1/resolve` 구현 완료
- 선택적 작가명 일치, 낮은 관련도 및 동명 작품 차단 구현 완료
- 최종 후보 하나만 상세 조회하도록 요청 흐름 개선 완료
- 후보 관련도보다 표지 유무가 우선되는 선택 오류 수정 완료
- 일치 유형, 메타데이터 품질, 부분 플랫폼 장애 정보 추가 완료
- 제목·작가 정규화 및 메타데이터 공통 후처리 추가 완료
- 판본·외전 표기를 하드 불일치에서 소프트 선택 우선순위로 변경 완료
- resolve 전체 제한시간과 외부 요청 동시성 제한 추가 완료
- 네이버 시리즈와 노벨피아의 고해상도 공개 표지 경로 적용 완료
- 플랫폼별 HTTP 연결 재사용과 앱 종료 정리 구현 완료
- 제목·작가 정확 일치 및 두 플랫폼 합의 기반 조기 확정 구현 완료
- 입력 순서를 보존하는 제한 병렬 `/api/v1/resolve/batch` 구현 완료
- 네이버 시리즈, 카카오페이지, 노벨피아, 리디 선택적 인증 검색 구현 완료
- 전용 브라우저 로그인, 플랫폼별 사용 설정 및 인증 세션 삭제 UI 구현 완료
- 19세 작품 인증 수집 장애와 해결 내역의 누적 문서화 시작
- 검색 결과와 표지를 확인하는 간단한 웹 UI 구현 완료
- Moya companion용 versioned health capability와 loopback local-development CORS 추가 완료
- resolve 전용 15분 opaque cover ref와 HTTPS host/redirect, 10MiB, JPEG/PNG/WebP 검증 endpoint 추가 완료
- 최소 파서 테스트와 대표 작품 실사이트 확인 완료
- 다음 플랫폼 후보는 미스터블루, 조아라 순으로 공개 검색 경로를 확인해 추가한다.
- 개인 사용 범위에서는 캐시를 추가하지 않으며 요청 간격 제한은 실제 필요성이 확인된 뒤 검토한다.
- 서버형 뷰어의 권장 인증 UX는 뷰어 내부 관리형 로그인 화면으로 확정했다. 다음 인증 작업은 Linux Docker Compose의 영구 프로필, Xvfb 창 모드 브라우저, 제한된 로그인 화면 전달과 명시적 인증 상태 API다.

## 목표

작품명을 입력받아 공개 웹페이지에서 가장 관련도 높은 웹소설 하나의 표지 URL과 핵심 메타데이터를 찾아 JSON으로 반환한다. 소설 뷰어에서 자동 적용할 수 있도록 애매한 결과는 성공으로 반환하지 않는다. 기본 실행은 DB 없이 동작하며 현재 문피아, 네이버 시리즈, 카카오페이지, 노벨피아, 리디를 지원한다.

## 첫 번째 MVP 범위

### 입력

- 작품명
- 작가명(선택)
- 일괄 요청 시 작품 목록(최대 50건)
- 19세 작품 포함 여부(선택, 기본값 `false`)

### 출력

- 제목
- 작가
- 플랫폼
- 플랫폼 작품 ID
- 작품 페이지 URL
- 표지 URL
- 작품 소개
- 장르
- 태그
- 연재 상태
- 검색어와의 일치 점수
- 수집 시각

### 제외

- DB 및 영구 캐시
- 검색 시 이미지 선다운로드, 임의 URL 프록시 또는 인증 제한을 우회하는 이미지 프록시
- 계정 아이디·비밀번호 직접 입력 또는 저장
- 로그인·성인 인증·CAPTCHA 우회
- 여러 플랫폼 작품의 자동 통합
- 별도 프론트엔드 프레임워크
- 복잡한 재시도 및 분산 요청 제어

## 구조

```text
HTTP API
  -> SearchService
      -> 플랫폼별 search() 병렬 실행
      -> 정확한 단일 후보 또는 두 플랫폼 합의 시 조기 확정
      -> 제목 관련도 우선, 같은 관련도에서 정보 완성도 비교
      -> 최종 후보 하나만 get_detail()
      -> 공통 메타데이터 후처리
  -> 단일 메타데이터 JSON 응답

선택적 인증 검색
  -> 전용 브라우저 프로필에서 사용자가 직접 로그인
  -> 활성화한 플랫폼의 19세 후보만 추가 검색
  -> 공개 검색 결과와 비교해 가장 적합한 결과 한 건 반환
```

Metadata용 별도 fetcher·영구 캐시·저장소 계층은 만들지 않는다. 표지만 예외로, resolve가 발급한 짧은 수명의
opaque ref를 allowlist·redirect·크기·MIME/magic 경계로 가져오는 `CoverFetcher`와 in-memory ref store를 둔다.

## 구현 단계

### 1. 프로젝트 골격

- Python 프로젝트 설정
- FastAPI 실행 진입점
- `/health`, `/api/v1/resolve`, `/api/v1/resolve/batch`와 진단용 `/api/v1/search` 엔드포인트
- 공통 Pydantic 모델

### 2. 문피아 수집기

- 공개 검색 페이지에서 후보 작품 추출
- 후보별 작품 ID와 상세 URL 추출
- 상세 페이지에서 핵심 메타데이터 추출
- 구조화 데이터, 메타 태그, CSS 선택자 순으로 필요한 값을 탐색

### 3. 검색 서비스

- 검색 후보 정규화
- 제목 기준 일치 점수 계산
- 전체 플랫폼에서 최종 후보 하나를 선정한 뒤 해당 후보만 상세 조회
- 수집 실패를 상태 정보로 변환

### 4. 최소 검증

핵심 구현이 끝난 뒤 다음만 한 번에 확인한다.

- 정규화 및 일치 점수의 핵심 사례
- API 응답 모델
- 대표 작품 한두 개의 실제 검색 및 표지 URL 반환

## 현재 완료 조건

- DB 설치 없이 서버가 실행된다.
- 작품명으로 다섯 플랫폼의 공개 작품을 병렬 검색할 수 있다.
- 자동 적용 API는 가장 일치하는 작품 하나만 반환한다.
- 정확도가 낮거나 동명 작품을 구분할 수 없으면 성공 결과를 만들지 않는다.
- 작가명을 선택적으로 전달해 동명 작품을 구분할 수 있다.
- 일치 방식과 상세 정보 품질을 호출자가 구분할 수 있다.
- 일부 플랫폼 검색 실패와 전체 실패를 구분할 수 있다.
- 조기 확정으로 생략한 플랫폼과 실패한 플랫폼을 구분할 수 있다.
- 여러 작품을 입력 순서대로 제한 병렬 처리할 수 있다.
- 최소한 제목, 작가, 작품 URL과 표지 URL을 반환한다.
- 작품을 찾지 못하거나 문피아 요청이 실패해도 유효한 JSON 응답을 반환한다.
- 필요한 최소 테스트가 통과한다.
- 인증 검색을 끄면 기존 공개 검색 경로와 속도에 영향이 없다.
- 인증 검색은 사용자가 플랫폼별 사용을 명시적으로 켠 경우에만 실행된다.

## 이후 확장 순서

현재 기능을 실제로 사용한 뒤 다음 작업을 검토한다.

1. 미스터블루 수집기 추가
2. 조아라 공개 검색 경로 확인 및 수집기 추가
3. 필요할 때만 플랫폼별 요청 간격 제한
4. HTTP 수집이 불가능하다고 확인된 플랫폼에만 Playwright 검토
