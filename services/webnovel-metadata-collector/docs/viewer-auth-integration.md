# 소설 뷰어용 19세 인증 API 연동

이 문서는 소설 뷰어가 웹소설 메타데이터 수집기를 로컬 API로 사용할 때의 현재 인증 방식과 상태 판단 규칙을 설명한다. 플랫폼 계정이나 쿠키를 뷰어가 직접 저장하는 방식은 사용하지 않는다.

## 현재 Moya companion 단계

현재 companion service의 로컬 인증 API와 전용 브라우저 프로필은 Moya의 기본 비활성
`웹소설 표지·작품 정보` 익스텐션 설정 화면에 연결되어 있다. Companion 프로세스 자동 실행과 설치 패키지
sidecar는 아직 구현하지 않았다. 현재 로컬 흐름은 다음과 같다.

1. 사용자가 `설정 → 익스텐션`에서 해당 익스텐션과 `19세 검색 결과 포함`을 켠다.
2. 플랫폼별 `로그인 창 열기`가 companion의 로그인 API를 호출한다.
3. 사용자가 별도 전용 Chrome/Edge 창에서 로그인·성인 인증·2단계 인증을 직접 완료한다.
4. 사용자가 Moya에서 `로그인 완료·사용`을 누르면 broker가 완료/활성화 API를 호출한다.
5. 이후 `include_adult=true` 검색은 저장된 전용 프로필을 재사용한다.
6. 현재는 검색 오류와 수동 `상태 새로고침`을 확인한 뒤 사용자가 `다시 로그인`을 선택한다. 명시적인
   `expired` 상태와 자동 재연결 안내는 후속 범위다.

Moya는 계정 비밀번호, 쿠키와 브라우저 저장소를 입력받거나 읽지 않는다. 저장 세션 전체 삭제는 되돌리기 어려운
동작이므로 별도 확인을 받는다. companion은 현재 단일 사용자·단일 전용 프로필을 전제로 하며 인터넷에 직접
노출하지 않는다.

## 결정된 권장안

Linux Docker Compose에서 한 명이 사용하는 서버형 소설 뷰어는 다음 사용자 흐름을 기본으로 한다.

1. 사용자가 뷰어에서 `네이버 시리즈 연결` 또는 `노벨피아 연결`을 누른다.
2. 뷰어 내부에 서버가 관리하는 해당 플랫폼 로그인 화면이 열린다.
3. 사용자가 로그인, 성인 인증과 휴대폰 2단계 인증을 직접 완료한다.
4. 뷰어가 연결 완료를 표시하고 로그인 화면을 닫는다.
5. 서버 수집기가 인증 프로필을 영구 볼륨에 보관해 이후 검색에 자동으로 재사용한다.
6. 세션이 만료됐을 때만 같은 연결 화면을 다시 표시한다.

사용자에게 SSH, VNC 주소, Docker 명령, 브라우저 확장 설치나 쿠키 복사를 요구하지 않는다. Xvfb와 화면 전달 구성은 내부 구현일 뿐 사용자 인터페이스에 노출하지 않는다.

## 현재 프로그램 기반과 미구현 범위

이 권장안은 소설 뷰어만 수정해서 완성할 수 없다. 수집기, Docker Compose와 소설 뷰어가 역할을 나눠 구현해야 한다.

| 영역 | 현재 상태 | 담당할 작업 |
| --- | --- | --- |
| 수집기 인증 프로필 | 구현됨 | 전용 프로필 생성, 저장, 삭제와 재사용 |
| 수집기 인증 API | 구현됨 | 상태 조회, 로그인 창 시작, 완료, 플랫폼 활성화, 세션 삭제 |
| 인증 검색 | 구현됨 | 네이버 시리즈·카카오페이지·노벨피아·리디 인증/성인 후보 검색 |
| 로그인/검색 프로필 잠금 제어 | 구현됨 | 로그인 창과 검색 컨텍스트가 같은 프로필을 동시에 열지 않도록 제어 |
| Linux 컨테이너 실행 | 미구현 | Chrome/Chromium, Playwright와 Linux 실행 경로 지원 |
| 영구 볼륨 경로 설정 | 미구현 | 인증 데이터 디렉터리를 환경 변수로 받아 Compose 볼륨에 연결 |
| 가상 화면의 창 모드 브라우저 | 미구현 | Xvfb에서 로그인 및 검색 브라우저를 `headless=False`로 실행 |
| 로그인 화면 전달 | 미구현 | 뷰어가 사용할 제한된 화면·입력 전달 경로와 단기 세션 토큰 |
| 명시적 인증 상태 | 미구현 | `connecting`, `ready`, `expired`, `failed` 등 플랫폼별 상태 반환 |
| 로컬 Moya 설정 UI | 구현됨 | 연결 확인, 플랫폼별 로그인 완료·재로그인·사용 중지·상태 갱신·세션 삭제 |
| 서버형 로그인 UI | 미구현 | Linux/Docker용 로그인 화면 전달과 verified/expired 상태 표시 |
| Compose 보안·저장소 | 배포 작업 | 내부 네트워크, 영구 프로필 볼륨, 외부 직접 노출 차단 |

현재 Windows UI에서 성공한 인증 방식은 최종 구조의 기반이다. 이미 수집기가 전용 브라우저를 열고 사용자의 수동 로그인을 기다린 뒤 같은 프로필을 검색에 재사용한다. 새로 필요한 핵심은 그 로그인 창을 Linux 가상 화면에서 실행하고, 소설 뷰어 안에 안전하게 표시하는 부분이다.

책임 분담은 다음과 같다.

- 수집기: 브라우저 실행, 프로필·쿠키 보관, 인증 상태와 검색 API 제공
- Docker Compose: Chrome/Xvfb 실행 환경, 영구 볼륨과 내부 네트워크 제공
- 소설 뷰어: 연결 버튼, 로그인 화면, 완료 및 오류 상태를 사용자에게 제공

따라서 “인증 자체”는 수집기에서 해결하고 “사용자 경험”은 소설 뷰어에서 해결한다. 어느 한쪽만 변경해서는 완성되지 않는다.

## 권장 구성

소설 뷰어와 수집기를 같은 사용자 PC에서 실행한다.

```text
소설 뷰어
  -> 127.0.0.1의 수집기 API
      -> 공개 플랫폼 HTTP 요청
      -> 필요한 플랫폼만 전용 브라우저 프로필 사용
```

- 뷰어는 수집기를 로컬 사이드카 프로세스로 실행하거나 이미 실행 중인 수집기에 연결한다.
- 플랫폼 로그인 창, 브라우저 프로필과 쿠키는 수집기가 관리한다.
- 뷰어는 플랫폼 아이디, 비밀번호 또는 쿠키를 입력받거나 저장하지 않는다.
- 인증 API와 `include_adult=true` 요청은 로컬 호출만 허용된다.
- 원격 서버나 웹 서버에서 여러 사용자의 인증을 대신 처리하는 구조로는 사용하지 않는다.

아래 예시는 현재 기본 주소인 `http://127.0.0.1:8000`을 사용한다. 실행 포트가 다르면 기준 주소만 바꾼다.

## 뷰어에 자체 인증 기능이 필요한가

Windows 데스크톱 뷰어라면 플랫폼별 인증 코드를 따로 만들 필요는 없다. 뷰어에는 다음 기능만 있으면 된다.

- 수집기 로컬 프로세스 실행 및 상태 확인
- 로그인 창 열기 API 호출
- 사용자에게 로그인 완료 버튼 제공
- 완료·검색·세션 삭제 API 호출

여러 사용자가 접속하는 웹 서버형 또는 모바일 뷰어는 하나의 서버 계정으로 인증을 대신 처리하면 안 된다. 사용자의 Chrome/Edge 프로필과 성인 인증이 필요한 구조이므로 사용자별 로컬 동반 프로그램이나 격리된 인증 설계가 필요하다. 개인용 단일 계정 서버는 아래 방식으로 서버에 세션을 둘 수 있다.

## 서버에서 구동되는 소설 뷰어

공개 작품 수집기는 소설 뷰어와 같은 서버에서 실행하는 편이 단순하다. 뷰어 서버는 외부에 공개하고 수집기 API는 `127.0.0.1`에만 바인딩해 두 프로세스끼리 호출한다. 현재 로컬 요청 검사는 외부 공개용 인증 수단이 아니므로 수집기 포트를 그대로 인터넷에 노출하면 안 된다.

19세 인증 방식은 서버 형태에 따라 달라진다.

### 개인용 Windows 서버이며 원격 데스크톱을 사용할 수 있는 경우

현재 구현을 가장 적게 바꾸는 방법이다.

1. 소설 뷰어와 수집기를 같은 Windows 서버에서 실행한다.
2. 서버의 수집기 API는 `127.0.0.1`에서만 연다.
3. 최초 인증 또는 세션 만료 시 서버에 원격 데스크톱으로 접속한다.
4. 인증 브라우저 열기 API를 호출하고 서버에 열린 전용 Chrome/Edge에서 직접 로그인한다.
5. 로그인 완료 API를 호출한 뒤 원격 데스크톱 연결을 종료한다.
6. 이후 서버의 수집기가 저장된 전용 프로필을 재사용한다.

한 명이 개인 계정 하나를 사용하는 서버라면 이 구성이 현재 가장 현실적이다. 브라우저 프로필 디렉터리는 서버의 영구 디스크에 두고 백업이나 저장소에는 포함하지 않는다.

### Linux VPS 또는 GUI가 없는 Docker 서버인 경우

현재 구현을 그대로 사용할 수 없다. 로그인 API가 서버에 설치된 시스템 Chrome/Edge의 보이는 창을 여는 방식이기 때문이다.

가능한 선택지는 두 가지다.

1. 서버에 가상 화면과 원격 브라우저 화면을 제공하고 사용자가 그 화면에서 직접 로그인한다. 컨테이너를 재생성해도 인증 프로필이 사라지지 않도록 별도 영구 볼륨이 필요하다.
2. 사용자 PC에 로컬 인증 브리지를 두고, 브리지가 인증 검색을 수행한 결과만 서버로 전달한다. 쿠키나 브라우저 프로필 자체는 서버로 전송하지 않는다.

개인용 서버에서 가끔 재인증하는 정도라면 첫 번째가 구현량이 적다. 서버에 GUI 구성 자체를 두고 싶지 않거나 사용자별 계정이 필요하면 두 번째가 더 안전하지만 별도 브리지와 통신 프로토콜이 필요하다.

Docker 컨테이너 내부 파일은 교체될 수 있으므로 인증 프로필은 반드시 영구 볼륨에 둬야 한다. 인증 상태에는 계정을 가장할 수 있는 민감한 쿠키가 들어 있으므로 이미지, Git 저장소, 로그 또는 API 응답에 포함하지 않는다.

### Linux Docker Compose의 운영자용 대안: Xvfb/noVNC

다음 구성은 서버에서 세션을 직접 만들어야 할 때 사용할 수 있는 운영자용 대안이다. 사용자가 SSH 터널이나 noVNC를 직접 다루게 하는 제품 UX로는 사용하지 않는다.

```text
Docker Compose
  ├─ novel-viewer
  └─ metadata-collector
       ├─ FastAPI
       ├─ Chrome/Chromium
       ├─ Playwright
       ├─ Xvfb 가상 화면
       ├─ noVNC 로그인 화면
       └─ auth-profile 영구 볼륨
```

서버가 headless여도 인증 브라우저까지 headless로 실행할 필요는 없다. Chrome은 `headless=False`로 Xvfb 가상 화면에 띄우고, 사용자가 필요할 때만 noVNC로 접속한다. 로그인과 2단계 인증은 사용자가 직접 처리하며 자동화하지 않는다.

권장 인증 흐름:

1. 뷰어 관리 화면에서 플랫폼 인증 시작을 누른다.
2. 수집기가 Xvfb의 전용 Chrome을 일반 창 모드로 연다.
3. 사용자는 SSH 터널 또는 인증된 관리 경로를 통해 noVNC 화면에 접속한다.
4. 로그인, 성인 인증과 휴대폰 2단계 인증을 직접 완료한다.
5. 완료 API가 로그인용 Chrome을 닫고 프로필 잠금 해제를 기다린다.
6. 수집기는 같은 영구 프로필을 Playwright의 창 모드 컨텍스트로 다시 연다.
7. 이후 작품 검색만 자동화하고 세션 만료 전까지 프로필을 재사용한다.

검색 컨텍스트도 Xvfb 위의 창 모드로 유지하는 이유는 사이트가 headless 브라우저만 별도로 차단할 가능성을 줄이기 위해서다. 화면을 실제로 계속 전송할 필요는 없으며 Xvfb 안에서만 실행하면 된다.

구현 시 필요한 변경:

- 인증 데이터 경로를 환경 변수로 지정해 Compose 영구 볼륨에 연결한다.
- Linux의 Chrome/Chromium 실행 파일과 `DISPLAY` 환경 변수를 지원한다.
- 서버 모드에서는 검색 컨텍스트를 `headless=False`로 실행할 수 있게 한다.
- noVNC 포트는 외부에 직접 공개하지 않고 `127.0.0.1` 바인딩 후 SSH 터널 또는 인증된 뷰어 관리 화면으로만 접근한다.
- Chrome 프로필은 한 시점에 로그인 브라우저 또는 검색 컨텍스트 하나만 열도록 기존 프로필 잠금 제어를 유지한다.
- 컨테이너 이미지와 Playwright 패키지의 브라우저 버전을 고정한다.

Compose에서 로그인 화면 구성 요소를 선택 서비스로 분리한다면 `auth` 프로필을 사용해 평소에는 실행하지 않고 재인증할 때만 켤 수 있다. 다만 수집기 컨테이너에 Docker 소켓을 마운트해 다른 컨테이너를 직접 제어하지 않는다.

2단계 인증은 이 구조의 장애물이 아니다. 휴대폰 승인이나 일회용 코드는 noVNC 화면의 실제 로그인 과정에서 사용자가 직접 처리한다. 아이디, 비밀번호와 2단계 인증 코드를 환경 변수나 수집기 설정으로 전달하지 않는다.

한계도 있다. 데이터센터 IP 자체가 차단되거나 CAPTCHA가 반복되면 2단계 인증 성공 여부와 관계없이 서버 브라우저 로그인이 불가능할 수 있다. 이 경우에만 사용자 PC의 로컬 인증 브리지가 인증 검색을 수행하고 메타데이터 결과만 서버에 전달하는 방식을 대안으로 검토한다.

### 일반 브라우저 세션을 서버로 직접 전달할 수 없는 이유

사용자가 자신의 브라우저에서 네이버나 노벨피아에 로그인해도 해당 로그인 쿠키는 플랫폼 도메인에만 속한다. 소설 뷰어 웹페이지는 다른 도메인의 쿠키, 특히 `HttpOnly` 쿠키를 읽어서 서버로 전달할 수 없다. 로그인 팝업을 열었다가 뷰어로 돌아오는 것만으로도 플랫폼 세션은 서버에 전달되지 않는다.

네이버·카카오의 공식 OAuth 로그인은 외부 애플리케이션용 사용자 인증과 허용된 Open API 토큰을 발급한다. 이 토큰을 시리즈·카카오페이지 웹 세션 쿠키로 바꾸는 공식 경로는 현재 사용하지 않는다.

따라서 확장이나 로컬 프로그램을 설치하지 않는 조건에서는 서버가 소유한 브라우저에서 사용자가 로그인해야 한다.

### 제품 UX 우선안: 뷰어에 내장된 관리형 로그인 브라우저

사용자에게 SSH, VNC 주소, Docker 명령이나 별도 원격 데스크톱을 노출하지 않는다. 뷰어의 인증 설정 화면이 서버 브라우저의 로그인 화면을 한시적으로 표시한다.

사용자 흐름:

1. 뷰어 설정에서 `네이버 시리즈 연결`을 누른다.
2. 뷰어 안에 네이버 로그인 화면이 모달 또는 새 페이지로 열린다.
3. 사용자가 로그인과 휴대폰 2단계 인증을 직접 완료한다.
4. 뷰어가 연결 완료를 표시하고 로그인 화면을 닫는다.
5. 서버는 해당 브라우저 프로필을 영구 볼륨에 보관해 이후 검색에 재사용한다.
6. 세션이 만료되면 같은 연결 화면만 다시 보여준다.

내부 구현은 Xvfb의 서버 Chrome 화면을 제한된 세션으로 스트리밍하는 방식이지만, 사용자에게 범용 원격 데스크톱 UI를 보여주지 않는다. 로그인 대상 도메인만 허용하고 세션마다 짧은 수명의 접근 토큰을 사용한다. 로그인 완료 후 스트리밍 연결과 로그인용 브라우저를 닫고, 같은 프로필로 자동 검색 컨텍스트를 연다.

이 방식은 별도 설치가 없고 현재 Docker 서버가 세션을 직접 소유한다는 장점이 있다. 반면 로그인 화면 스트리밍, 입력 전달과 접근 제어가 필요하므로 단순 API보다 구현량이 크다. 사용자가 입력한 비밀번호와 2단계 인증 코드는 서버 브라우저에 직접 전달하되 애플리케이션 로그나 DB에 저장하지 않는다.

### 대안: 브라우저 확장 인증 브리지

서버 브라우저에 계정 정보를 입력하는 것을 원하지 않을 때 선택할 수 있는 대안이다. 다만 사용자가 확장을 설치해야 하므로 현재 단일 사용자 서버의 기본 UX로 삼지 않는다.

```text
사용자 브라우저 확장
  ├─ 사용자의 평소 플랫폼 로그인·2단계 인증 세션 사용
  └─ 서버로 outbound HTTPS/WebSocket 연결
          ↓
소설 뷰어 서버
  ├─ 공개 작품은 서버에서 직접 수집
  └─ 세션 필요 작품만 확장에 검색 작업 전달
```

사용자 흐름:

1. 뷰어에서 `19세 작품 연결`을 누른다.
2. 뷰어가 일회용 연결 코드를 표시하고 브라우저 확장을 연다.
3. 확장이 네이버 시리즈 또는 노벨피아의 일반 브라우저 탭을 연다.
4. 사용자가 평소처럼 로그인, 성인 인증과 휴대폰 2단계 인증을 완료한다.
5. 확장은 서버와 연결된 상태만 표시한다. 비밀번호와 쿠키를 서버로 보내지 않는다.
6. 이후 뷰어에서 작품을 검색하면 공개 플랫폼은 서버가 처리하고, 세션이 필요한 플랫폼 요청만 확장이 사용자 브라우저 세션으로 처리한다.
7. 확장이 꺼져 있거나 세션이 만료되면 뷰어는 `인증 브리지 연결 필요` 상태와 재연결 버튼을 표시한다.

서버가 사용자의 브라우저에 직접 접속할 수 없으므로 확장이 서버로 outbound 연결을 유지하거나 짧게 폴링해야 한다. 단일 사용자 환경에서는 일회용 연결 코드로 장기 토큰을 발급하고 사용자가 뷰어 설정에서 토큰을 폐기할 수 있게 한다.

이 방식의 장점:

- 사용자에게 원격 데스크톱, SSH, noVNC 또는 Docker 명령을 노출하지 않는다.
- 로그인 화면과 2단계 인증이 사용자의 평소 브라우저에서 동작한다.
- 서버에 플랫폼 비밀번호나 세션 쿠키를 저장하지 않는다.
- 데이터센터 IP 대신 사용자 브라우저의 정상 접속 환경을 사용한다.
- 평소 검색은 자동으로 처리되고 세션 만료 때만 다시 로그인한다.

대가도 있다. Chrome/Edge 확장을 한 번 설치해야 하고, 네이버 시리즈와 노벨피아 도메인 접근 권한이 필요하다. 확장과 서버 사이의 연결 토큰 및 작업 소유권 검증도 구현해야 한다. 이 변경은 기존의 “기본 브라우저 프로필을 사용하지 않는다”는 정책을 바꾸므로 사용자 동의와 권한 설명이 필요하다.

확장은 쿠키 조회·내보내기 권한을 요구하지 않는 방향을 우선한다. 허용된 플랫폼 도메인에서 로그인된 요청을 수행하고 필요한 작품 메타데이터만 구조화해 서버로 돌려준다. 원본 쿠키, 전체 브라우저 프로필과 계정 비밀번호는 전송하지 않는다.

### 여러 사용자가 사용하는 서버인 경우

현재 구조를 그대로 사용하면 안 된다. 현재는 서버 전체가 하나의 브라우저 프로필과 `enabled_platforms` 설정을 공유하기 때문이다.

- 사용자별로 분리된 프로필과 저장 경로가 필요하다.
- 사용자 A의 인증 결과가 사용자 B의 검색에 사용되지 않도록 요청 소유권을 검증해야 한다.
- 수집기 API 자체에도 뷰어 서버만 호출할 수 있는 인증이 필요하다.
- 세션 삭제, 만료와 재로그인도 사용자별로 처리해야 한다.

이 요구가 없다면 개인용 단일 계정 구조를 유지하고 복잡한 다중 사용자 인증을 추가하지 않는다.

### 현재 권장안

| 운영 환경 | 권장 방식 |
| --- | --- |
| 개인용 Windows 서버 + 원격 데스크톱 | 수집기를 서버에 함께 실행하고 서버에서 한 번 직접 로그인 |
| 개인용 Linux Docker Compose | 뷰어에 내장된 서버 관리형 로그인 브라우저 |
| 서버에 계정 입력을 원하지 않는 경우 | 브라우저 확장 또는 로컬 인증 브리지 |
| 관리 화면 구현 전 임시 운영 | 서버의 Xvfb/noVNC 인증 화면 |
| 다중 사용자 서비스 | 현재 구조 사용 금지, 사용자별 인증 설계가 먼저 필요 |

## 현재 인증 방식

1. 수집기가 시스템 Chrome 또는 Edge를 프로그램 전용 프로필로 실행한다.
2. 사용자가 열린 브라우저에서 직접 로그인과 성인 인증을 완료한다.
3. 뷰어가 로그인 완료 API를 호출한다.
4. 수집기가 로그인 창을 종료하고 같은 프로필을 headless 검색 컨텍스트로 다시 연다.
5. 이후 검색은 저장된 세션을 재사용한다. 로그인 만료 전까지 매 검색마다 로그인하지 않는다.

전용 프로필은 Windows에서 다음 경로에 저장된다.

```text
%LOCALAPPDATA%\WebNovelMetadataCollector\auth\browser-profile
```

플랫폼 사용 설정은 같은 `auth` 폴더의 `settings.json`에 저장된다. 계정 비밀번호는 저장하지 않으며 수집기가 쿠키 값을 직접 추출해 API 응답으로 노출하지도 않는다.

## 뷰어가 구현할 상태 흐름

### 1. 기능 상태 조회

```http
GET /api/v1/auth/status
```

응답 예시:

```json
{
  "available": true,
  "browser_running": false,
  "enabled_platforms": ["naver_series", "novelpia"],
  "last_error": null
}
```

필드 의미:

- `available`: Playwright 선택 의존성과 인증 기능을 실행할 수 있다는 뜻이다. 로그인 성공을 뜻하지 않는다.
- `browser_running`: 사용자가 조작하는 전용 로그인 창이 열려 있다는 뜻이다. 검색용 headless 컨텍스트는 이 값에 포함하지 않는다.
- `enabled_platforms`: 사용자가 인증 검색을 사용하도록 켠 플랫폼이다. 현재 세션이 유효하다는 보장은 아니다.
- `last_error`: 마지막 브라우저 준비 오류다.

지원 플랫폼 키는 `naver_series`, `kakao_page`, `novelpia`, `ridi`다.

### 2. 로그인 창 열기

```http
POST /api/v1/auth/naver_series/open
Content-Type: application/json

{"requested": true}
```

플랫폼 키만 바꿔 같은 API를 사용한다. 호출이 성공하면 전용 시스템 브라우저가 해당 플랫폼 로그인 페이지에서 열린다. 뷰어는 “브라우저에서 로그인과 성인 인증을 마친 뒤 완료를 누르세요”라는 안내를 표시한다.

### 3. 로그인 완료 및 플랫폼 사용 설정

사용자가 완료를 눌렀을 때 호출한다.

```http
PUT /api/v1/auth/naver_series
Content-Type: application/json

{"enabled": true}
```

이 호출은 다음 작업을 순서대로 수행한다.

1. 로그인 전용 브라우저 프로세스를 종료한다.
2. 프로필 잠금이 해제될 때까지 짧게 기다린다.
3. 같은 프로필을 검색용 headless 컨텍스트로 연다.
4. 플랫폼을 `enabled_platforms`에 저장한다.

프로필을 열 수 없으면 `409`를 반환하고 플랫폼을 활성화하지 않는다. 단, 성공 응답도 브라우저 프로필을 열 수 있었다는 뜻이며 해당 플랫폼의 로그인 유효성을 미리 확정한 것은 아니다.

플랫폼 사용만 끌 때는 로그인 창 없이 다음과 같이 호출한다.

```http
PUT /api/v1/auth/naver_series
Content-Type: application/json

{"enabled": false}
```

### 4. 19세 작품 검색

```http
GET /api/v1/resolve?q=작품명&include_adult=true
```

작가명을 알면 잘못된 동명 작품 적용을 줄이기 위해 함께 전달한다.

```http
GET /api/v1/resolve?q=작품명&author=작가명&include_adult=true
```

일괄 적용도 작품별로 `include_adult`를 지정한다.

```http
POST /api/v1/resolve/batch
Content-Type: application/json

{
  "items": [
    {"query": "일반 작품", "include_adult": false},
    {"query": "19세 작품", "author": "작가", "include_adult": true}
  ]
}
```

## 인증 성공 판정

현재 API에는 별도의 로그인 검증 완료 토큰이 없다. 다음 필드를 함께 사용해야 한다.

- `authenticated_search=true`: 활성화된 인증 검색 분기가 실패하지 않고 실행됐다는 뜻이다. 목표 작품이 19세 작품이라는 증명은 아니다.
- `failed_platforms`: 인증 플랫폼 실패는 `naver_series_auth`, `kakao_page_auth`, `novelpia_auth`, `ridi_auth`처럼 `_auth` 접미사로 표시된다.
- `platform_errors`: 로그인 만료, 성인 인증 필요, Cloudflare 또는 응답 오류의 사용자용 메시지가 들어간다.
- `metadata.tags`의 `19금`: 최종 선택 결과가 인증 검색에서 확인된 19세 후보임을 뜻한다.

뷰어의 권장 판정 순서는 다음과 같다.

1. `status=found`이고 `metadata.tags`에 `19금`이 있으면 19세 작품 메타데이터 수집 성공으로 처리한다.
2. 요청한 플랫폼의 `${platform}_auth`가 `failed_platforms`에 있으면 인증 재연결 안내를 표시한다.
3. `authenticated_search=true`지만 `status=not_found`이면 인증은 실행됐으나 작품을 찾지 못한 것으로 처리한다. 로그인 성공으로 단정하지 않는다.
4. `status=found`지만 `19금` 태그가 없으면 공개 검색에서 선택된 일반 작품일 수 있으므로 일반 결과로 취급한다.
5. `status=ambiguous`면 자동 적용하지 않고 사용자 선택 또는 작가명 입력을 요구한다.

예시:

```json
{
  "status": "found",
  "authenticated_search": true,
  "failed_platforms": [],
  "platform_errors": {},
  "metadata": {
    "platform": "naver_series",
    "platform_work_id": "14445233",
    "tags": ["19금"]
  }
}
```

| 노벨피아 | 인증된 검색 JSON과 상세 HTML | 필요 | `아포칼립스의 암컷조련사`, ID `426992` |
| 리디 | 공식 검색 API 일반 HTTP 응답에서 19세 후보 분리 | 실제 검색에는 불필요 | `상수리나무 아래`, ID `1922000007` |

리디는 headless 브라우저가 Cloudflare 403을 받기 때문에 일반 HTTP 경로를 사용한다. 현재 공통 API 구조에서는 리디도 `enabled_platforms`에 들어 있어야 인증 검색 분기가 실행된다. 이는 플랫폼 로그인 성공을 의미하는 것이 아니라 사용자가 19세 검색을 명시적으로 허용했다는 게이트 역할이다.

따라서 현재 리디만 연동할 때는 로그인 창을 열지 않고 `PUT /api/v1/auth/ridi`에 `{"enabled": true}`를 보내도 된다. 다만 공통 구현상 Playwright와 시스템 Chrome/Edge가 설치되어 있어야 한다. 이 불필요한 의존성은 향후 `public_adult` 모드로 분리할 개선 대상이다.

카카오페이지와 리디는 향후 로그인 불필요 플랫폼으로 분리할 수 있다. 현재 뷰어를 연동할 때는 위의 실제 API 계약을 기준으로 구현한다.

## 세션 종료와 삭제

열려 있는 로그인 창과 검색 컨텍스트만 닫고 저장 프로필은 유지한다.

```http
POST /api/v1/auth/browser/close
Content-Type: application/json

{"requested": true}
```

저장된 전용 프로필, 쿠키와 플랫폼 사용 설정을 모두 삭제한다.

```http
DELETE /api/v1/auth/session
```

세션 삭제는 로그아웃과 같은 복구가 어려운 작업이므로 뷰어에서 별도 확인을 받는 것이 좋다.

## 오류 처리

- `403`: 브라우저의 외부 Origin 또는 cross-site 요청이다. 수집기와 같은 PC의 로컬 앱에서 호출해야 한다.
- `404`: 지원하지 않는 플랫폼 키다.
- `409`: 로그인 브라우저 프로필이 아직 잠겨 있거나 검색 컨텍스트를 준비하지 못했다.
- `422`: 필수 요청 본문 또는 작품명 형식이 잘못됐다.
- `503`: Playwright 선택 의존성 또는 시스템 Chrome/Edge를 사용할 수 없다.

플랫폼 세션이 만료되면 다시 `POST /auth/{platform}/open`부터 진행한다. 뷰어는 계정 정보 입력창을 만들지 않는다.

## 현재 한계와 개선 후보

현재 `enabled_platforms`는 설정값이고 `authenticated_search`는 인증 분기 실행 결과이므로 인증 상태 표현이 완전히 명시적이지 않다. 뷰어 연동이 본격화되면 다음 필드를 API에 추가하는 것이 좋다.

- 플랫폼별 `auth_mode`: `none`, `public_adult`, `browser_session`
- 플랫폼별 `auth_state`: `disabled`, `ready_unverified`, `verified`, `expired`, `failed`
- 마지막 실제 인증 성공 시각과 재로그인 필요 여부

이 필드들은 현재 수집 기능에 필수는 아니므로 아직 구현하지 않았다. 지금은 이 문서의 판정 규칙과 기존 응답 필드를 사용한다.
