# 표지·목록·확장 저장소 용량 재검토

검토일: 2026-09-21. 운영 코드 `ef56860` 기준. 제품 코드 수정·배포는 하지 않았다. 운영 저장 데이터는 값 대신 크기만 확인했고, TOTAL 인기/최신 목록을 기존 API로 조회했다. 조회 과정에서 소스의 정상 캐시 갱신은 일어날 수 있다.

## 결론

표지 누락을 일으킬 수 있는 캐시 퇴거 결함을 재현했다. 용량 확대만으로 해결할 문제는 아니다. 큰 원본 표지를 그대로 보관하는 현재 방식에서 브라우저 32MiB는 재사용 예산으로 작다. 사용 중인 이미지 수명 보호와 실패 복구를 먼저 고치고, 목록용 썸네일로 비용을 줄이는 것이 우선이다.

TOTAL 목록 오류는 별도로 다룬다. 이전 답변의 `source_storage_limit` 확정 진단은 철회한다. 당시 HTTP 422/32바이트 기록만으로 오류 종류를 확정할 수 없으며, 이번 운영 인기/최신 조회는 모두 성공했다.

## 확인한 사실

### 1. 표지 주소를 화면에 붙이기 전에 퇴거할 수 있음 — 재현

- `src/external-sources/session-cover-cache.ts:98`: `document.images`에 있는 Blob URL만 퇴거에서 보호한다. 다운로드 완료 후 호출자에게 전달 중이거나 React가 화면에 반영하기 전인 URL은 보호하지 않는다.
- 표시 중인 3MiB Blob 7개를 보호 목록에 두고, 3MiB Blob 4개를 동시에 resolve했다. 합계 33MiB가 되면서 새 URL 하나가 취소됐다. 호출자가 받은 URL을 실제 Node Blob URL fetch로 확인한 결과는 `[false, true, true, true]`였다.
- 재현 파일: `/tmp/moya-cover-budget-review.ts`. 운영 캐시 클래스를 그대로 호출했다. 이미지 데이터는 크기를 맞춘 합성 Blob이며 JPEG 디코딩이나 사용자 브라우저 화면까지 재현한 검사는 아니다. 확인한 대상은 URL 수명 결함이다.
- 실제 탐색 표지 동시 요청 수도 4개다. 앞선 실측에는 3,345,480바이트 원본 표지가 있어 용량 조건은 현실적이다. 다만 이번 사용자의 개별 실패가 같은 원인이었는지는 브라우저 증거가 없다.

대응: 요청 중·화면 사용 중인 소비자가 이미지를 붙잡고 있는 동안 캐시 퇴거가 URL을 취소하지 않도록 수명을 관리한다. 짧은 타이머로 취소를 미루는 임시 처방보다 소비자 해제 시점을 명확히 한다. 로그아웃/소스 세대 변경은 별도 무효화 경로로 유지한다.

### 2. 표지 실패 후 복구가 부족함 — 코드 확인

- `src/features/discovery/DiscoveryCard.tsx:38`: 표지 조회 실패를 무시한다.
- 같은 파일 `:60`: 이미지 로딩 오류는 `failed=true`로 바꾸고 끝난다. 같은 카드가 화면에 계속 있으면 실패만으로 재조회하지 않는다. 화면 밖으로 나갔다 돌아오거나 카드/세션이 바뀌면 다시 시도할 수 있다.
- 캐시에 30초 실패 보관이 있으므로 무조건 즉시 재호출하면 같은 실패를 받는다.

대응: 취소된 Blob URL은 유효 캐시를 다시 획득하고, 일시적인 네트워크 실패는 화면에 있는 카드에 한해 제한된 재시도를 제공한다. 명시적 재시도는 해당 항목의 실패 보관을 우회한다. 인증 실패/없는 이미지는 반복 요청하지 않는다. 정상 표지가 있으면 새 표지가 준비될 때 교체한다.

### 3. TOTAL 내부 저장 한도는 작은 편이나 이번 장애 원인은 미확정

운영 설치본: TOTAL 토끼 만화 0.1.13, 원본 JS SHA-256 `f1d33f361e18801ec152f66f81a6af53751a6d7c0e7ffc1859a28ca2036163b3`.

- 확인 당시 저장값 JSON: **178,062바이트(약 174KiB), 144키**. 상한 262,144바이트의 약 68%다.
- 큰 값: 상태 데이터 77,822바이트, 작품 연결표 54,000바이트, 한 작품의 회차 경로 14,340바이트, 연결표 조각 7,116바이트. 값의 내용/자격 증명은 기록하지 않았다.
- 캐시 우회 API 조회: 인기 HTTP 200/26항목, 최신 HTTP 200/46항목. 이번에는 `source_storage_limit`를 재현하지 못했다.
- `mangayomi/host.ts:606–617`: 실행이 성공해도 변경값 또는 합쳐진 저장값이 256KiB를 넘으면 결과 반환 전에 실패한다. 따라서 앞으로 커지는 데이터가 목록·상세·회차 요청을 막을 수는 있다. 기존 저장값이 상한 미만인 것만으로 과거 초과 시도를 배제할 수 없다.
- 설치 JS는 작품별 정보와 회차 경로를 SharedPreferences에 쌓는다. 일부 데이터의 TTL은 재조회 여부를 판단하며, 오래된 키를 자동 삭제하는 일반 LRU 정책은 아니다. 이 저장소에는 로그인/사용자 설정뿐 아니라 다음 요청에 필요한 참조 정보도 들어갈 수 있다.

대응: 호환 확장의 저장소를 일반 표시용 캐시처럼 임의 삭제하지 않는다. 우선 확장당 **2MiB를 검토 시작값**으로 삼되 실제 여러 작품/긴 회차 데이터로 확인한다. 전역 무제한 확대는 하지 않는다. 현재 게스트 입력/출력 JSON 1MiB, 암호화 저장 파일 1MiB, 호출당 변경 키 256개, 전체 키 2,048개 등 연관 경계도 함께 맞춰야 한다. 256KiB 숫자 하나만 바꾸면 다른 한도에서 실패한다. 사용자 설정 폼의 48KiB 제한은 별개이므로 그대로 둔다.

장기적으로 명시적인 임시 캐시 API/구분을 제공하는 것은 유효하지만, 기존 Mangayomi의 모든 SharedPreferences 키를 이름만 보고 캐시라고 간주하지 않는다. 특히 작품/회차 연결 정보를 지우거나 저장 실패를 무시하고 성공 결과만 반환하는 처리는 후속 열람을 깨뜨릴 수 있다.

### 4. 원인을 가리는 목록 오류 문구 — 코드 확인

`useExternalSourceController.ts:1058`은 TextServerRequestError 외의 오류를 일반적인 연결 실패 문구로 바꾼다. 하위 계층에 `source_storage_limit` 전용 메시지가 있어도 이 화면에서는 사라질 수 있다.

대응: 알려진 오류 코드를 보존해 용량/인증/네트워크를 구분한다. 서버에는 코드·소스 식별자·크기 같은 최소 진단 정보만 남기고, 원본 응답·설정값·토큰은 남기지 않는다. 과거 422 응답을 바이트 수만으로 추정하지 않아도 되도록 한다.

## 용량 정책 판단

아래는 payload 예산이다. JS 객체, 이미지 디코딩, 동시 다운로드 메모리까지 포함한 프로세스 전체 메모리 상한이 아니다.

| 계층                             | 현재                                          | 판단 / 권장                                                                                                        |
| -------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 브라우저 표지                    | 32MiB / 200개 목표                            | 큰 원본에는 작다. URL 수명 수정 후 64MiB / 400개를 초기 상한 후보로 사용. 썸네일 도입 후 모바일 메모리를 보고 조정 |
| 서버 표지                        | 프로세스 128MiB / 1,000개, 계정 64MiB / 500개 | 우선 유지. 썸네일로 단위 크기를 줄이면 같은 예산의 재사용 폭이 커짐. 재사용 실패 측정 없이 무작정 확대하지 않음    |
| 서버 목록·상세·회차 JSON         | 프로세스 32MiB / 1,000키, 계정 16MiB          | 현재 유지. 퇴거돼도 정상 조회 결과 자체는 반환됨                                                                   |
| 브라우저 탐색 메모리 / IndexedDB | 8MiB / 32MiB                                  | 현재 유지. 저장 실패가 조회 실패로 이어지지 않는 흐름 유지                                                         |
| Mangayomi 확장 내부 상태         | 확장당 256KiB / 2,048키                       | 영속적인 호환 상태에는 부족해질 수 있음. 2MiB 후보와 관련 전송·암호화 한도를 함께 검증                             |

브라우저 표지는 현재 DOM에 있는 URL을 보호하므로 32MiB가 이미 절대 상한은 아니다. 64MiB로 올릴 때도 표시 중인 이미지를 깨뜨리는 강제 퇴거로 상한을 맞추면 안 된다.

표지 1개가 3MiB면 32MiB에 약 10개, 64MiB에도 약 21개뿐이다. 가령 목록용 표지가 평균 100KiB가 되면 200개가 약 20MiB다. 후자는 설명용 계산이며 실제 압축률을 측정한 결과는 아니다. 첫 원본 다운로드 비용은 서버 썸네일만으로 없어지지 않지만, 이후 전송·보관·디코딩 비용은 줄일 수 있다.

서버에서 목록용 표지를 표시 크기에 맞춰 축소해 재사용하는 것을 권장한다. 예: 폭 320–480px 후보, 비율 유지, 확대하지 않음. 본문 이미지는 이 정책 대상이 아니다. 변환 실패 시 원본 반환, 처리 동시성/디코딩 픽셀 상한, 기존 인증·프록시·계정 격리를 지킨다. 별도 Redis나 새 캐시 서비스는 필요하지 않다.

현재 신선도 정책(표지 24시간/이전 결과 최대 7일, 인기 30분, 최신 2분, 검색 10분, 회차 2분)은 이번 증상 때문에 바꿀 근거가 없다. 용량/URL 수명 문제를 TTL 연장으로 해결하지 않는다. 메모리 표지는 탭/프로세스 종료로 사라지지만 IndexedDB와 확장 내부 상태는 재시작 이후에도 남는다.

## 수정 우선순위와 최소 확인

1. 표지 URL 소비자 수명 보호, 실패 복구, 원인별 오류 표시. 위 용량 경계 재현과 실제 화면 스크롤/왕복만 집중 확인.
2. 브라우저 표지 64MiB 후보 및 서버 목록용 썸네일. 큰 표지의 최초/재방문 전송량과 모바일 메모리 확인.
3. Mangayomi 상태 용량과 관련 한도 정합성 조정. TOTAL 여러 작품의 상세/회차와 재시작 후 열람을 확인. 기존 로그인/설정/회차 참조를 보존하고 상한 초과 시 부분 저장하지 않음.

세 작업 모두 별도 전체 플랫폼 검사 반복이나 새로운 캐시 관리 UI 없이 진행 가능하다. 운영 데이터 전체 초기화는 해결책으로 제안하지 않는다.

## 구현 결과 — 2026-09-21

브랜치 `fix/source-cover-cache-lifecycle`에서 구현했다. 위 절은 검토 당시 상태이며 아래가 최종 변경이다. 운영 컨테이너는 교체하지 않았다.

- 브라우저 표지 예산을 **64MiB / 400개**로 조정했다. 요청 소비자의 AbortSignal이 살아 있는 동안 URL을 보호하며, 다운로드 완료 직후에도 보호가 적용되어 DOM 반영 전 퇴거를 막는다. 소비자가 떠나면 보호를 해제하고 미사용 항목부터 제거한다. 화면/소비자가 계속 사용하는 표지는 예산을 일시적으로 초과할 수 있다.
- 탐색 카드가 보이는 동안 일시적 네트워크 실패를 최대 두 번 재시도한다(2.5초, 5초). 카드 제거/화면 이탈 시 취소한다. 인증 실패는 자동 재시도하지 않는다. 일시적 실패의 캐시 수명은 2초, 그 외는 기존 30초다. 이미지 표시 자체가 실패한 경우 재획득을 한 번 시도한다.
- 서버 표지는 **480×720px 안에 비율을 유지**해 WebP 품질 82로 변환한다. 작은 표지는 유지하고 확대·자르기를 하지 않는다. 원본이 더 작으면 원본을 사용한다. 디코딩은 24MP 이하, 변환은 동시 2개/대기 8개/5초 제한이며 과부하·변환 실패 시 원본을 반환한다.
- Mangayomi/APK는 변환된 표지를 기존 서버 표지 캐시에 넣는다. `.moyaext`도 서버 표지 응답에서 변환한다. 후자는 기존 브라우저 캐시를 재사용하며 별도 서버 썸네일 캐시는 추가하지 않았다. 만화 본문/회차 다운로드 바이트는 변환하지 않는다.
- Mangayomi 상태는 **2MiB / 8,192키**다. 호출당 변경 키도 같은 검증 경계를 사용한다. 해당 호환 프로필의 게스트 입력/출력만 4MiB로 확장했고 일반 확장의 1MiB 경계는 유지했다. 암호화 파일은 문자열 이중 인코딩을 감안해 4MiB+64KiB로 맞췄다. 사용자 설정 폼 48KiB는 유지했다. 한도 초과 시 기존 상태를 보존하며 임의 캐시 키 삭제/부분 저장은 하지 않는다.
- 알려진 용량 오류를 목록 화면까지 전달한다. 서버에도 허용된 오류 코드만 기록하고 설정값/토큰/원본 응답은 기록하지 않는다.
- 서버 이미지 처리 의존성 `sharp@0.34.5`를 고정하고 lockfile, 배포 의존성 라이선스 목록, 플랫폼별 목록 비교를 함께 갱신했다. 새 테스트는 기존 CI 작업에 포함했다.
