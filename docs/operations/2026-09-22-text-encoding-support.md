# 텍스트 가져오기 인코딩 확대

## 문제와 범위

기존 TXT·Markdown 가져오기는 UTF-8과 EUC-KR만 선택할 수 있었다. UTF-16은 BOM이 있어도 올바르게 처리하지 못했다. 또한 현재 Node/ICU의 `TextDecoder('euc-kr')`는 CP949 확장 한글을 완전히 처리하지 않는다. 실제 CP949 바이트 `8C 63`을 `똠`이 아닌 `\u008Cc`로 해석하는 것을 재현했다. 사용자 문제 파일 자체는 받지 않았으므로 그 파일의 원인까지 확정한 것은 아니다.

## 구현

- 기존 UTF-8, CP949/EUC-KR에 UTF-16 LE/BE, Shift_JIS/Windows-31J, EUC-JP, ISO-2022-JP, GB18030/GBK, Big5, Windows-1252, Windows-1251을 추가했다.
- 자동 감지는 UTF BOM을 먼저 확인한다. BOM 없는 UTF-16은 앞부분 16KiB에서 반복되는 ASCII/공백의 0바이트 위치와 디코딩 유효성이 뚜렷한 경우만 감지한다. 나머지는 기존 UTF-8 → 한국어 감지 방식을 유지한다. 일본어·중국어·서유럽 인코딩을 자동으로 판정한다고 주장하지 않는다.
- CP949 확장 한글을 네이티브 디코더가 제대로 지원하는지 검사하고, 미지원 환경에서만 `@kayahr/text-encoding` 2.2.0의 EUC-KR 모듈로 해석한다. 전역 TextDecoder는 교체하지 않는다. 전체 언어 테이블/Node Buffer 폴리필은 추가하지 않는다. 새 의존성은 MIT이며 라이선스 목록을 갱신했다. 브라우저 타입 검사의 모듈 해석도 기존 서버·스크립트와 같은 Bundler로 맞춰 패키지의 공개 exports를 사용한다. 패키지의 browser 조건에서는 네이티브 EUC-KR 디코더만 사용하고, Node 환경의 기본 조건에서만 CP949 보완 모듈을 포함한다. 공유 코드 경계도 해당 진입점만 허용한다.
- 선택값은 가져오기·미리보기·서버 업로드·저장된 원본 재해석·ID 마이그레이션 경로에 동일하게 전달된다. 서버는 지원하지 않는 인코딩 값을 업로드 전에 거절한다. 기존 DB 문자열 컬럼을 사용하므로 스키마 변경은 없다.
- 가져오기 UI는 기존 선택 메뉴를 확장하고 짧은 안내만 추가했다. 기존 작품의 본문을 자동 재해석하거나 덮어쓰지 않는다. 잘못 가져온 작품은 올바른 인코딩으로 다시 가져와야 한다.

## 제한 및 검증

- 인코딩 자동 판별은 확정적이지 않다. BOM 없는 비 ASCII UTF-16이나 언어가 모호한 파일은 직접 선택해야 한다. UTF-32 BOM은 UTF-16으로 잘못 읽지 않고 UTF-8 변환을 안내한다. UTF-32·Johab·혼합 인코딩 파일의 완전 지원은 범위에 포함하지 않는다.
- TXT 크기 한도와 기존 파싱 방식은 변경하지 않는다. 아카이브의 4GiB 지원과 별개다.
- 11개 인코딩의 실제 고정 바이트(확장 한글 `똠`, 일본어 확장 문자 `髙`, 중국어/이모지 포함), 일반/증분 파서, UTF-16 BOM 유무, 기존 UTF-8과 동일한 본문/문단 ID, 서버 선택값 저장 및 잘못된 값 거절을 검사했다. 관련 7개 파일 134개 테스트가 통과했다.

- 웹·서버·스크립트 타입 검사, 변경 파일 lint/format, 공유 코드 경계 검사 및 웹·서버 production build를 통과했다. 웹 산출물 검사도 통과했으며 초기 JS gzip은 이전 656,264bytes에서 656,906bytes로 약 642bytes만 늘었다. 운영 서비스/작품은 변경하지 않았다.
