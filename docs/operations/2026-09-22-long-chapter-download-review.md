# 긴 만화 회차 다운로드와 작은 표지 후속 수정

## 확인한 원인

- 운영 로그에서 TOTAL 토끼 만화의 `prepared-images` 요청이 HTTP 422로 실패했다. 파일이 준비된 뒤 진행하는 import job 자체는 성공했다.
- 운영 확장 0.1.13과 설정을 임시 복사본으로 열어 `원펀맨 리메이크 02권`을 확인했다. 서재·진행률·설치 상태는 변경하지 않았으며, 인증/설정 변경도 메모리에만 반영했다.
- 이 확장은 브라우저로 원문 회차를 열어 이미지 주소를 수집한다. 그 과정에서 본문 이미지도 로딩되는데, 브라우저의 일반 요청용 32MiB 전송 한도를 넘으면 `source_body_limit`으로 실패했다(재현 약 27초).
- 용량 한도를 조정한 다음에는 기존 33초 안에 페이지 로딩과 수집 스크립트를 모두 실행해야 하는 제한도 확인했다. 브라우저의 오류를 확장이 자체 메시지로 바꾸면 호스트가 `execution_failed`로만 전달하던 문제도 있었다.

## 변경

- 호스트가 호출한 이미지 회차 수집(`pages`)에만 브라우저 예산을 별도로 적용한다. 브라우저 전송량 512MiB(본문·HTML/JS/TLS·중복 요청 포함), 최대 2,048 이미지 + 부가 요청 512개다. 일반 목록·상세·소설 호출은 기존 32MiB/512 요청을 유지한다. 확장이 WebView 인자로 한도를 높일 수는 없다.
- 이미지 수집은 확장의 요청 시간에 탐색 준비 여유 30초를 더하되 기존 WebView 최대 90초와 상위 작업 취소/시간 제한을 유지한다. 해당 확장의 33초 요청은 총 63초가 된다.
- 브라우저 용량·시간 초과 등 허용된 오류 코드가 확장 내부 오류 처리 뒤에도 유지되도록 한다. 원문 오류나 인증정보는 UI에 노출하지 않는다.
- 작은 표지는 이미지 크기를 유지하고 제목 12px, 하단 상태 11px, 작업 버튼 28px, 진행 막대 2px로 조정했다. 실패 상태는 줄바꿈 없는 상태명과 필요한 경우 다음 줄에 놓이는 작업 버튼으로 처리한다. 일반 표지/목록 레이아웃은 유지한다.

## 검증

- 수정 후 같은 실제 회차의 이미지 목록 207개를 약 30초에 수집했고, 207개 모두 정상 이미지로 다운로드했다(32,699,809 bytes, 약 31.2MiB). 진단에서는 요청을 순차 실행해 전체 약 124초가 걸렸다. 운영 경로의 기존 이미지 동시 처리 수 3은 변경하지 않았다. 이 검사는 수집·다운로드까지이며 서재 가져오기/진행률 저장은 실행하지 않았다.
- 관련 프록시/호환 런타임 테스트: 18개. 실제 로컬 전송으로 일반 40MiB 차단, 이미지 수집 40MiB 허용, 이미지 수집 513MiB 차단을 확인한다. 원문 확장이 오류를 바꿔 던지는 경우도 검증한다.
- 실제 LibraryScreen을 Chrome 320/390/1366px, 어두운 테마로 표시해 실패 카드 포함 가로 넘침/페이지 오류가 없음을 확인했다.
- 서버 타입 검사, 변경 파일 lint, CSS 검사, 포맷 검사로 검증 범위를 제한한다.

## 제한

이번 조정은 확인된 긴 회차 수집 실패 경로를 해결한다. 원문 사이트의 접속 실패나 인증 요구까지 보장하지는 않는다. 이미지 자체의 개별/합산 크기 제한, 수집 브라우저 동시 실행 수, 취소 처리는 그대로 유지한다. 운영 배포는 별도다.

## 한도 및 뷰어 복구 후속 조정

- 최초 수정의 브라우저 예산 288MiB는 512MiB로 상향했다. 이것은 브라우저가 중간 페이지와 이미지를 받는 **전송 예산**이다. 완성된 회차의 본문 이미지 합산 256MiB, 이미지 한 장 20MiB, 최대 2,048장 제한과는 별개다. 브라우저 전송 허용량 전체를 API 메모리에 보관하는 구조는 아니다.
- Mangayomi 본문 이미지의 요청 제한을 15초에서 30초로 늘렸다. 표지의 제한은 유지한다.
- 내부 웹 Nginx의 소스 다운로드/준비/조립 경로 대기를 300초에서 720초로 늘렸다. 클라이언트의 기존 10분 작업 제한보다 내부 프록시가 먼저 끊는 상황을 줄인다. 일반 API는 그대로다.
- 만화 이미지에 페이지별 `다시 불러오기`를 제공한다. 데스크톱 도구 모음과 모바일 문서 메뉴에는 `현재 화면 다시 불러오기`를 제공한다. 문서 전체를 닫거나 읽기 위치를 초기화하지 않고 현재 페이지 및 주변 로딩 대상만 갱신한다.
- 이미지 요청은 60초 후 오류와 재시도 상태가 된다. 취소를 무시하는 저장소 요청도 로딩 큐를 영구 점유하지 않도록 하고, 늦게 도착한 이전 요청은 표시하지 않는다. 응답은 성공했지만 브라우저가 이미지 디코딩에 실패한 경우도 오류 상태로 전환한다.
- 실제 사용자 회색 화면의 원인을 확정한 것은 아니다. 확인한 복구 불가능 경로를 보완했고, 요청 실패·미완료 및 이미지 디코딩 실패를 주입해 검증한다.

### 수 GB 로컬 만화는 별도 작업

확장 회차의 256MiB 제한을 로컬 만화책 전체에 그대로 적용하는 것은 아니다. 로컬 업로드는 이미 16MiB 청크를 사용하며 현재 운영 전체 업로드 한도는 500MiB다. 이미지 아카이브 파서는 최대 5,000페이지, 이미지 한 장 64MiB, 압축 해제 합산 1GiB를 허용한다.

문제는 `apps/server/src/services/import-service.ts`가 청크 업로드 완료 후 `Buffer.allocUnsafe(expectedBytes)`로 파일 전체를 합친다는 점이다. 이어지는 ArrayBuffer/Blob 변환도 메모리를 더 쓸 수 있다. 운영 API 2GiB, import worker 3GiB 메모리 제한에서 업로드 용량만 수 GB로 올리면 안정적으로 처리할 수 없다.

후속 구현 순서는 다음으로 제한한다.

1. 업로드 청크를 디스크 임시 파일로 합치고 해시는 스트리밍으로 계산한다.
2. 아카이브를 파일 기반으로 열어 페이지를 하나씩 추출·저장한다. ZIP 외 RAR/7z도 파일 전체 메모리 로딩 여부를 확인한다.
3. 취소·실패 시 임시 파일과 미완성 데이터 정리를 보장하고, 디스크 용량 및 압축 해제 한도를 별도로 둔다.
4. 실제 대용량 파일에서 메모리 사용이 파일 크기에 비례하지 않음을 확인한 뒤 전체 업로드/아카이브 한도를 올린다.

이번 수정에는 대용량 가져오기 재설계나 운영 용량 제한 변경을 포함하지 않는다.

### 후속 검증

- 로더·이미지 훅·브라우저 프록시·Mangayomi 호스트 관련 4개 파일, 25개 테스트 통과. 미완료 요청 재시도, 60초 제한, 이전 응답 무시, 디코딩 오류 복구를 포함한다.
- 실제 만화 뷰어 컴포넌트의 모바일/PC 세로 보기와 모바일 페이지 보기에서 페이지 재시도 및 현재 화면 재로딩을 확인했다. 이미지 디코딩 오류 복구 후 같은 페이지의 좌표 변화는 0px였고 브라우저 오류도 없었다.
- 웹/서버 타입 검사와 격리된 Nginx 설정 검증을 통과했다. 운영 컨테이너와 데이터는 변경하지 않는다.
