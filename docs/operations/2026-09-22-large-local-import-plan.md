# 대용량 로컬 EPUB·ZIP·CBZ 가져오기

## 목표와 범위

Self-host 서버에서 이미지가 많은 EPUB과 일반 ZIP·CBZ를 파일당 4GiB까지 가져온다. 파일 크기만큼 메모리를 할당하지 않고, 기존 청크 업로드·작업 큐·데이터 확정 절차를 재사용한다. 운영 배포와 실제 사용자 데이터 변경은 이번 작업에 포함하지 않는다.

RAR·7z·PDF·브라우저 단독 가져오기 및 기존 작품에 회차를 합치는 경로는 이번 대용량 지원 대상에서 제외한다. 이 경로의 기존 제한을 유지한다. Moya 전용 내보내기 컨테이너는 일반 이미지 ZIP과 구분해 대용량이 지원되지 않으면 메모리에 읽기 전에 명확하게 거절한다.

## 현재 병목

- 업로드는 이미 청크 방식이나 import worker가 전체 파일을 Buffer로 합친다.
- 원본을 Blob으로 복사하고 원본 저장도 Buffer로 진행한다.
- EPUB은 참조 이미지 전체를 메모리에 보관한다. 압축 해제 합산 제한은 128MiB다.
- ZIP·CBZ는 페이지 순차 추출 기능이 있으므로 파일 기반 원본을 연결하면 재사용할 수 있다.
- 가져오기 worker 기본 동시 실행은 이미 1개다. 기존 설정을 유지하며 대용량 운영에서도 1개를 권장한다.

## 구현 순서와 완료 조건

- [x] 1. 파일 기반 업로드 조립 및 원본 저장
  - 실행 시도별 임시 파일, 스트리밍 SHA-256, 청크 크기 검증, 취소 및 실패 정리.
  - 디스크 여유 확인과 명확한 오류; 원본 S3 저장은 길이가 알려진 스트림 사용.
  - 기존 작은 파일/이어 붙이기 동작을 유지한다.
- [x] 2. EPUB 이미지 순차 처리와 ZIP·CBZ 연결
  - EPUB 본문·메타데이터는 기존 파서를 유지하고 이미지 바이트를 한꺼번에 보유하지 않는다.
  - 기존 리소스 식별자/해시를 유지한다. 필요하면 이미지 해시 조사와 저장에 두 번 읽는 비용을 허용한다.
  - 압축 해제 합산과 텍스트 합산, 개별 이미지, 항목 수 제한을 분리한다. 취소·압축 손상 검증을 유지한다.
- [x] 3. 업로드 허용 범위와 사용자 안내
  - 지원하는 일반 EPUB·ZIP·CBZ만 4GiB, 압축 해제 합산 8GiB까지 허용한다.
  - 다른 형식은 기존 500MiB 기본 제한을 유지한다. 관리자의 기존 명시적 설정은 보존한다.
  - 실제 서버 경로에서 파일을 통째로 읽는 프런트엔드/서버의 남은 우회 경로를 확인한다.
- [x] 4. 필요한 검증과 마무리
  - 조립 무결성/취소 정리, EPUB 기존 결과 일치 및 순차 처리, 형식별 업로드 제한의 회귀 검사.
  - 격리 환경에서 1GiB 이상 EPUB 및 수 GiB ZIP·CBZ를 처리하고 최고 메모리/저장 결과를 기록한다.
  - 관련 타입 검사 및 변경 범위 검사. 전체 플랫폼·브라우저 검사 반복은 하지 않는다.
  - 각 단계의 결과 및 제한을 이 문서에 업데이트하고 커밋한다.

## 자원과 실패 정책

원본 보관 및 추출 이미지 저장은 유지하므로 최종 저장량이 원본의 약 두 배일 수 있다. 업로드 청크와 조립 파일이 처리 중 함께 존재해 임시 공간도 필요하다. 디스크 부족·잘못된 압축 파일·취소는 기존 서재를 변경하지 않고 실패해야 한다. 무제한 해제/이미지 크기를 허용하지 않는다. 메모리가 파일 크기에 비례하지 않는다는 검증 없이 한도만 올려 완료 처리하지 않는다.

## 진행 기록

- 계획 작성. 기존 다운로드/뷰어 재시도 수정은 `5fabfb4`, `379e5c6`이며 이 작업은 그 뒤에 별도 커밋으로 쌓는다.

- 1단계: 업로드 파일을 실행별 임시 파일로 조립하고 SHA-256을 스트리밍 계산한다. 원본은 파일 기반 Blob/길이가 알려진 S3 스트림으로 저장한다. 관련 24개 테스트와 서버 타입 검사 통과. 취소·크기 불일치 시 자기 실행의 임시 파일만 제거한다.

- 2단계: EPUB 리소스는 해시 조사 후 한 장씩 다시 읽어 기존 자산 ID·본문·표지와 같은 결과로 저장한다. 서버 ZIP·CBZ도 파일 기반 Blob을 사용한다. EPUB 텍스트 합산 128MiB, 항목당 32MiB, ZIP 이미지당 64MiB 등 개별 안전 제한은 유지한다.
- 3단계: `MAX_ARCHIVE_UPLOAD_BYTES` 기본 4GiB를 추가했다. 기존 `MAX_UPLOAD_BYTES`는 기타 형식/회차 추가에 적용하며 신규 설정은 관리자가 낮출 수 있다(최대 4GiB). 대용량 Moya 복원 파일과 ZIP으로 이름만 바꾼 다른 형식은 eager 처리 전에 거절한다. 브라우저 회차 병합 미리보기의 전체 파일 읽기도 500MiB 초과 파일에서는 건너뛴다.
- 중간 검증: 기존 가져오기·EPUB 및 파일 처리 46개 테스트, 업로드 정책/프런트엔드 병합 관련 75개 테스트 통과. 추가한 4GiB init 경계 검사 및 최종 검사는 다음 기록에서 확정한다.

## 대용량 실측 결과

운영과 연결하지 않은 별도 Docker 네트워크, PostgreSQL·MinIO 및 worker 이미지에서 확인했다. worker 메모리 제한은 1GiB, Node heap 제한은 512MiB다. 동일한 노이즈 PNG를 서로 다른 페이지 이름으로 넣은 실제 디코딩 가능한 합성 자료이며 ZIP은 store 방식이다.

| 형식 |                 원본 bytes | 이미지 수 | 가져오기 시간 | 프로세스 최대 RSS |
| ---- | -------------------------: | --------: | ------------: | ----------------: |
| EPUB | 1,134,493,182 (약 1.06GiB) |        90 |        35.3초 |            281MiB |
| CBZ  | 2,268,967,842 (약 2.11GiB) |       180 |        43.4초 |            286MiB |

시간은 업로드 청크 준비 완료 후 worker 가져오기 기준이다. 원본 MinIO 크기, 모든 자산의 DB 저장 수, 표본 이미지 재조회·디코딩, 완료 상태 및 임시 업로드 폴더 제거를 확인했다. cgroup 최고 사용량은 디스크 페이지 캐시를 포함해 약 1GiB였으며 OOM은 없었다. RSS와 컨테이너 전체 사용량은 다른 값이다. 두 배 파일에서 비슷한 RSS를 확인했지만 모든 압축 방식/본문 구조의 메모리 상한을 보장하는 수치는 아니다.

4GiB는 허용 상한이며 HTTP upload-init에서 정확한 경계 허용/초과 거절을 확인했다. 4GiB 전체 파일의 실제 가져오기까지 수행했다는 뜻은 아니다. CRC, 해시, 항목별 크기와 전체 해제 제한은 유지한다.

수동 재현 진입점은 `apps/server/src/services/testing/large-local-import-smoke.ts`다. 기본 CI에는 추가하지 않는다. `MOYA_LARGE_IMPORT_SMOKE=1`과 `moya-large-import-`로 시작하는 격리 DB/S3 호스트만 허용한다. 해당 임시 DB에 기존 migration을 먼저 실행한 뒤 server의 tsx로 스크립트에 `epub` 또는 `cbz` 인자를 전달한다. 임시 컨테이너/저장소를 폐기하는 검사이며 운영 연결에는 사용하지 않는다.

## 기존 방식과 자원 비교 (2026-09-22)

기존 `379e5c6`과 파일 기반 구현 `d604b30`을 동일한 파일로 각각 두 번 실행했다. 두 번째는 실행 순서를 뒤집었다. 기존 제한에서도 허용되는 EPUB 100,844,982bytes(이미지 8장), CBZ 403,372,034bytes(32장)를 사용했다. 별도 PostgreSQL·MinIO와 매번 새 worker 컨테이너에서 실행했고, 양쪽 모두 CPU 2개·메모리 3GiB·Node heap 2GiB로 맞췄다. 운영 서비스와 데이터는 변경하지 않았다.

| 자료          | 방식             | 평균 처리 시간 | 평균 worker CPU 시간 | 프로세스 최대 RSS 범위 |
| ------------- | ---------------- | -------------: | -------------------: | ---------------------: |
| 약 96MiB EPUB | 기존 메모리 조립 |         2.55초 |               2.61초 |             612–615MiB |
| 약 96MiB EPUB | 새 파일 조립     |         3.02초 |               4.37초 |             264–265MiB |
| 약 385MiB CBZ | 기존 메모리 조립 |         7.43초 |               8.04초 |         1,454–1,466MiB |
| 약 385MiB CBZ | 새 파일 조립     |         6.89초 |               9.76초 |             270–286MiB |

시간은 청크 준비 후 가져오기 완료까지이며 네트워크 업로드 시간은 제외한다. CPU 시간은 worker의 user+system 누적 시간으로, 병렬 작업 때문에 경과 시간보다 클 수 있다. DB·MinIO의 CPU는 포함하지 않는다. 모든 실행에서 원본 크기, 자산 수, 표본 이미지 재조회·디코딩 및 임시 파일 정리를 확인했다.

- EPUB: 처리 시간 약 18%, CPU 시간 약 68% 증가; 최대 RSS 약 57% 감소. 기존 자산 식별자를 유지하면서 이미지를 해시 조사와 저장에 두 번 읽는 비용이 있다.
- CBZ: 처리 시간 약 7% 감소, CPU 시간 약 22% 증가; 최대 RSS 약 81% 감소. 파일 기반 읽기 비용은 늘지만 큰 Buffer 조립과 복사가 없어 전체 경과 시간이 줄었다.
- 임시 디스크: 파일 크기를 F라 하면 기존 청크 약 F에서, 새 방식은 청크+조립 파일 약 2F로 늘어난다. 원본과 추출 이미지의 최종 저장량은 양쪽이 같다. 처리 완료/실패 시 실행별 조립 파일을 정리한다.
- 가져오기 중 worker의 `write_bytes` 증가량은 새 방식만 EPUB 100,847,616bytes, CBZ 403,374,080bytes였다. 이는 파일 한 개 분량의 추가 쓰기이며 실제 디스크에 영구 기록된 양이나 SSD 속도 측정은 아니다. 페이지 캐시와 삭제 전 쓰기 취소가 개입한다. 이번 비교는 cold-cache 디스크 벤치마크가 아니다.
- 프로세스 RSS가 줄어도 파일 페이지 캐시는 메모리를 사용한다. 이는 회수 가능한 캐시이며 컨테이너 전체 메모리와 RSS를 혼동하지 않는다.

앞선 큰 파일 측정에서 1.06GiB EPUB의 약 35초 중 조립·해시는 2.8초, 분석은 12.0초, 원본 저장은 4.1초, 이미지 처리는 16.2초였다. 2.11GiB CBZ의 약 43초 중 조립·해시는 5.5초, 원본 저장은 7.7초, 이미지 처리는 29.8초였다. 따라서 전체 시간을 임시 파일 쓰기 비용으로 볼 수 없다. 조립 단계에도 해시 계산이 포함된다.

판단: 수 GiB 지원과 서버 메모리 여유를 위해 새 방식을 유지한다. 작은 EPUB의 CPU·처리 시간만 보면 기존 방식이 유리하지만, 큰 파일에서는 전체 메모리 적재가 제약이다. 추가 최적화가 필요하면 EPUB의 이미지 재읽기를 먼저 검토하되, 이번 비교 때문에 별도 소형/대형 처리 경로를 추가하지 않는다. 결과는 이 서버의 store 방식 합성 파일 두 종류에 한정되며 압축률, 이미지 수, HDD/NAS 등의 환경에 따라 달라진다. 기존 구현은 큰 EPUB/CBZ를 원래 제한 그대로 처리할 수 없어 수 GiB 파일과 직접 비교하지 않았다.

## 적용 및 남은 범위

### 후속 보완: 진행 표시와 공간 사전 확인

- 파일 조립 중 실제 처리 바이트를 기준으로 진행률을 갱신한다. DB 갱신은 기존 650ms 제한을 재사용하며 완료 시 마지막 값을 반영한다. 분석·원본 저장·이미지 저장·마무리는 짧은 상태 문구로 구분한다. 이미지 저장 진행은 처리 개수이며 전체 가져오기 완료율로 표시하지 않는다.
- 서버 진행 문구가 기존 작품 카드와 소스 회차의 상태 표시까지 전달되도록 연결했다. 카드에서는 `준비 40%`, `저장 45개`처럼 줄여 표시한다. 긴 문구는 작은 카드와 회차 상태 영역에서 말줄임 처리하며 새 전역 진행창이나 팝업은 추가하지 않았다. 기존 상세 가져오기 화면도 서버 분석·저장 중 업로드 바이트를 근거로 100%를 표시하지 않는다.
- 업로드 시작 전에 서버 uploads 디스크에서 파일 크기의 두 배(청크+조립 파일)와 64MiB 여유를 확인한다. 부족하면 세션 생성/파일 전송 전에 HTTP 507과 짧은 안내를 반환한다. 이는 공간 예약이 아니며 다른 작업으로 여유 공간이 변할 수 있어 조립 직전 재검사와 ENOSPC 처리를 유지한다. 별도 S3 저장소의 잔여 용량까지 보장하는 검사는 아니다.
- 백그라운드 동작은 기존 구조를 유지한다. 가져오기 창을 닫아도 작업은 계속되고, 완료 시 읽던 화면을 강제로 이동시키지 않는다. 브라우저가 파일을 전송하는 단계에서는 탭 종료/OS의 브라우저 중단에 영향을 받으며, 서버에 접수된 작업은 worker가 처리한다. 아직 가져오기가 완료되지 않은 새 작품을 즉시 읽을 수 있게 만드는 변경은 아니다.
- 확인: 관련 75개 테스트(공간 부족 사전 거절, 조립 진행/취소 정리, 상태 전달, 상세 화면 완료율, 창을 닫은 뒤 진행/화면 유지 포함), 웹·서버 타입 검사와 변경 TS lint 통과. 기존 라이브러리 컴포넌트로 320/390/1366px Chromium에서 작은 표지 진행 표시를 확인했고 가로 넘침·카드 하단 높이 증가·페이지 오류가 없었다. 운영 배포는 하지 않았다.

- 운영 배포는 하지 않았다. 다음 배포 때 Compose의 `MAX_ARCHIVE_UPLOAD_BYTES`가 적용된다. 이미 설정한 `MAX_UPLOAD_BYTES`는 기타 형식/회차 추가 한도로 유지한다.
- 대용량 파일은 별도 작품으로 가져온다. 기존 작품에 회차 추가·합치기, 중첩 압축, Moya portable restore, 전체 백업 복원 및 export의 기존 제한은 그대로다.
- 브라우저 단독/Android 로컬 가져오기는 기존 제한을 유지한다. 이번 지원은 self-host의 서버 가져오기 경로다.
- 자동 전체 테스트 추가 대신 실제 대용량 검사와 관련 회귀 검사만 실행했다. 실제 사용자 파일에 특이한 EPUB 구조가 있으면 해당 파일별 호환성 확인은 별도로 필요하다.

- 최종 확인: 업로드 init 경계 검사 포함 관련 122개 단위/회귀 검사와 기존 회차 추가 PostgreSQL/S3 통합 검사 1개가 통과했다. 웹·서버·스크립트 타입 검사, 변경 파일 lint, Compose 설정 검증 및 diff 검사도 통과했다. 검사에 사용한 임시 컨테이너/볼륨/네트워크는 정리했다.

### 후속: 대용량 회차 추가 및 EPUB 한 번 읽기

이 문서의 최초 지원 범위 이후 일반 EPUB·ZIP·CBZ의 서버 회차 추가와 EPUB 한 번 읽기를 구현했다. 최신 범위·실측·내보내기/백업 제한은 [회차 추가 계획 및 결과](2026-09-22-large-local-append-plan.md)를 따른다. `MAX_UPLOAD_BYTES`는 기존 delta/기타 형식에 유지하고, 새 `append_local_archive`에는 `MAX_ARCHIVE_UPLOAD_BYTES`를 적용한다.
