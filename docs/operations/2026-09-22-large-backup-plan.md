# 대용량 합본 내보내기와 백업·복원

원본 개별 다운로드(`a649523`)만으로 이전 검토의 1번 전체가 완료되는 것은 아니다. 남은 합본 ZIP과 앱 백업·복원을 같은 브랜치에서 이어 구현한다. 운영 서비스는 변경하지 않는다.

## 구현 순서

1. 백업의 개별 S3 객체를 버퍼 대신 스트림으로 ZIP64에 기록한다. 브라우저는 인증 후 일회용 주소로 바로 저장한다.
2. 복원 업로드를 디스크에 받고 ZIP 내부 원본도 디스크 파일로 검증한다. SHA-256·실제 해제 크기·경로 검증 후 기존 DB 트랜잭션/객체 정리 로직으로 복원한다. 메모리에 남는 JSON에는 별도 제한을 유지한다.
3. 검사한 백업은 짧게 보관해 복원 때 재업로드하지 않는다. 취소·만료·실패 시 해당 작업의 임시 파일만 정리한다.
4. 로컬 합본의 전체 원본 ZIP도 서버 ZIP64 스트림으로 제공한다. 각 EPUB/CBZ를 폴더별로 포함하며 한 EPUB로 재편집하지 않는다.
5. 기존 백업 호환·읽기 기록 복원·변조 거절·취소 정리와 512MiB/1,000항목 초과를 집중 검증한다. 격리 DB에서 실제 복원을 확인한다. 전체 플랫폼 검사는 반복하지 않는다.

## 자원 정책

- 백업 총 비압축 256GiB, ZIP 입력 257GiB, 100,000항목을 기본 지원 범위로 한다. 단일 객체는 기존 S3 단일 PUT에 맞춰 5GiB 이하이며 현재 일반 원본 업로드 4GiB를 포함한다.
- JSON 메타데이터는 항목당 64MiB, 전체 256MiB, manifest 16MiB까지. 바이너리 용량과 별개로 메모리 부담을 제한한다.
- 원본은 재압축하지 않고 ZIP 저장 방식으로 처리한다. 큰 EPUB/CBZ를 압축하느라 CPU를 소모하지 않는다.
- 복원에는 ZIP과 해제 원본을 위한 임시 디스크 공간이 필요하다. 검사 완료 후 ZIP은 지우고, 복원 완료/취소/만료 시 나머지를 지운다.
- 앱 라이브러리 백업은 원본·본문·독서 상태를 위한 기능이다. 운영 계정/암호화 키/확장 실행 파일을 포함한 서버 전체 재해복구 백업과 구분한다.

## 구현 결과

- `전체 백업 만들기`는 인증된 요청으로 발급한 60초 일회용 주소를 브라우저가 내려받는다. 계정 토큰을 URL에 넣지 않으며, 다운로드 시작을 완료로 기록하지 않는다.
- 기존 백업 v1 형식을 유지한다. ZIP64 출력에 S3 객체를 하나씩 스트리밍하고 크기와 해시를 확인한다. 원본은 압축하지 않는다.
- 백업 선택 시 ZIP 업로드를 디스크로 받고, 원본·표지·폰트 등의 바이너리를 생성한 임시 파일명으로 해제한다. 경로/중복/실제 해제 크기/CRC/SHA-256과 객체 메타데이터가 일치해야 검사 성공이다. ZIP 전체 해시는 업로드 중 계산해 추가 전체 읽기를 피한다.
- 검사한 파일은 30분간 재사용하며, 복원 요청에는 검사 ID와 충돌 처리 선택만 보낸다. 네트워크 오류 뒤 재시도도 같은 ID를 사용해 새 복원 작업을 중복 생성하지 않는다. 이미 처리한 ID는 재사용할 수 없다.
- 검사 결과를 원자적으로 가져간 뒤 복원한다. 삭제/만료 처리가 실행 중인 복원의 파일을 지우지 않는다. 기존 DB 트랜잭션, 충돌 정책, S3 정리 예약과 롤백을 유지한다.
- 한 API 프로세스에서 임시 백업 슬롯 2개, 백업 다운로드 1개, 복원 실행 1개로 제한한다. 업로드·검사 시간은 최대 1시간이다. 복원도 1시간 예산으로 원본 전송·행 처리·커밋 전에 중단 여부를 확인하고 초과 시 롤백한다. SQL 대기에도 문장별 1시간 제한을 둔다.
- 로컬 합본의 `원본 다운로드`에는 `전체 원본 ZIP 저장`이 추가된다. 권별 폴더에 원래 EPUB/CBZ를 그대로 보관하며 기존 브라우저의 500MiB ZIP 생성 제한을 거치지 않는다.
- DB 마이그레이션은 없다. Nginx의 백업 요청 크기 및 스트리밍 설정은 함께 반영해야 한다. 운영 서비스는 변경하지 않았다.

## 검증

- 백업·원본 다운로드·인증·관련 UI 집중 검사: 12개 파일 51개 테스트 통과. 기존 백업의 교체/복사/건너뛰기와 객체 정리 보호 검사 포함.
- 513MiB 원본 + 작은 원본 1,001개로 ZIP 생성 → 디스크 업로드 → 검사 → 원본 해시/크기 일치 확인. 기존 두 제한을 모두 넘는 회귀 검사다.
- 같은 경로를 `MOYA_BACKUP_STREAM_TEST_MIB=2050`으로 수동 실행해 **2,050MiB 원본 + 1,001개 작은 원본** 검증 통과(약 28초). 합성 바이트 스트림과 로컬 임시 디스크 검사이며, 실제 운영 S3/역방향 프록시를 포함한 성능 수치는 아니다.
- 별도 PostgreSQL에서 기존 EPUB/CBZ 합본 통합 검사 2개 통과. 실제 S3 SDK와 루프백 객체 저장소 fixture를 사용해 디스크 기반 백업을 복원하고, 원본 자산·읽기 위치·북마크를 확인했다. 이 복원 fixture의 파일 크기는 작다.
- 손상된 ZIP, 잘못된 인증/주소, 주소 재사용, 부분 업로드 취소, 검사 만료/폐기, 복원 중 폐기 경쟁을 확인했다. 완료 뒤 작업 임시 디렉터리가 비어 있는지 검사했다.
- 모바일 320/390px·PC 1366px 원본 화면과 브라우저 다운로드 검사, 웹/서버 타입 검사, 변경 파일 lint/format, Nginx 설정 검사 통과. 전체 플랫폼 검사나 운영 복원은 실행하지 않았다.

## 지원 경계

- 256GiB/100,000항목은 리소스 상한이다. 그 크기까지 실측한 보증이 아니며 메타데이터 크기·서버 디스크 여유·전송 시간 제한에 먼저 도달할 수 있다.
- 지원 확대는 Self-host 웹 경로다. 네이티브/기존 Blob 기반 내보내기는 작은 백업 보호 한도를 유지한다. 로컬 IndexedDB 백업이나 Cloud Vault 합본 호환을 확장한 작업은 아니다.
- 일반 라이브러리 백업이며 서버 계정·암호화 키·배포 설정·확장 실행 파일 전체의 재해 복구를 대신하지 않는다. 기존 허용 목록에 포함된 독서 설정/탐색 구성은 `reader_settings`로 보관한다.
- 검사 파일과 다운로드 주소는 API 프로세스 로컬이다. 재시작 뒤에는 파일을 다시 선택한다. 다중 API 인스턴스에 분산하는 구성과 중단 지점 이어받기는 별도다.
- 정상 종료/만료/취소/처리 오류는 작업 소유 임시 파일을 정리한다. 강제 종료·정전으로 남은 `DATA_DIR/backup-staging` 파일은 API를 멈춘 상태에서 운영자가 정리해야 한다. 다른 실행 중인 작업을 추정해 삭제하는 자동 orphan 정리는 추가하지 않았다.
- 라이브러리 원본이 백업 도중 삭제되거나 교체되면 스트림 검증이 실패할 수 있다. 브라우저 다운로드 완료 여부를 확인하고, 완료된 백업으로 대표 작품 복원을 확인한 뒤 보관한다.

## PR 최종 점검

외부 TLS 프록시용 `deploy/host-nginx.example.conf`도 백업 257GiB와 원본 다운로드 스트리밍에 맞췄다. 기존 정적 검사가 다른 location의 512MiB 문구로 잘못 통과하던 부분을 백업 location별 검사로 수정했다. 저장공간 조회·분류·공간 부족 검사를 기존 CI 선별 목록에 포함했다. 마지막 집중 검사 9개 파일·25개 테스트와 배포 설정 검사를 통과했다. 앞서 완료한 수 GiB·브라우저 검사는 다시 실행하지 않았다.
