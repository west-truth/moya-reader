## 제품 구조

목표는 **기존 self-host를 Windows에서 앱처럼 쓰는 것**입니다. 서재 한 곳을 여러 화면에서 이용합니다.

```text
서버가 없는 사용자: Windows 앱 → 앱에 포함된 기존 self-host → DB·원본 파일
                                      ↑
                             다른 기기의 브라우저

서버가 있는 사용자: Windows 앱 / 브라우저 → 사용 중인 self-host → DB·원본 파일
```

- 저장·가져오기·수집기·독서·AI/TTS·백업은 기존 공통 서버를 재사용합니다.
- 다른 기기 접속은 같은 서버의 주소와 로그인으로 처리합니다. LAN·터널·Tailscale 같은 연결 방식은 저장 모델과 독립적입니다.
- 서재 이전에는 백업·복원을 사용합니다. 두 서버에 따로 생긴 변경을 자동 병합하지 않습니다.
- 기존 브라우저 캐시와 서버 사이의 `/api/sync`, `/api/sync/events`는 계속 필요합니다. 서버 간 복제와 구별합니다.

**구현 사실:** 내장 서버 자동 시작과 공유 화면은 있습니다. 앱 시작 시 기존 서버 주소를 선택하는 화면은 아직 없습니다.
위 두 번째 경로는 목표 구조이며, 브라우저의 기존 self-host 직접 접속은 이미 가능합니다.

## 필요성과 비용 판단

| 작업                                           | 판단                               | 근거                                                                                             |
| ---------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------ |
| 내장 self-host의 시작·종료·설치·데이터 보존    | 필요                               | 서버를 별도 설치하지 않고 로컬에서 사용하기 위한 앱 경계                                         |
| 기존 서버 직접 접속                            | 필요, 후속 UI 작업                 | 이미 서버가 있는 사용자는 같은 서재를 그대로 이용해야 함                                         |
| 같은 서버의 원격 접속                          | 필요                               | PC를 켜 두고 다른 기기에서 읽는 요구                                                             |
| 기존 백업으로 자료 이전                        | 필요                               | 서버를 옮기는 일회성 작업                                                                        |
| 독립 서버 간 원본·주석·삭제의 양방향 자동 복제 | 현재 범위에서 제외                 | 두 서재를 독립 편집해야 하는 요구가 없고, 모든 새 데이터 종류마다 충돌·삭제·재시도를 구현해야 함 |
| 대용량 IndexedDB를 별도 네이티브 저장소로 교체 | 현재 데스크톱의 선행 과제에서 제외 | 실제 자료는 기존 서버의 DB·파일 저장소가 담당                                                    |

기능을 추가하기 전에 사용자에게 **어떤 사용 흐름이 필요한지, 기존 경로로 가능한지, 변경할 공통 코드와 유지비가 무엇인지** 설명합니다.
공유 코드를 쓴다는 이유만으로 새로운 동기화 모델을 추가하지 않습니다. 과거 W01~W12는 현재 완료 목록이 아닙니다.

## 남은 필요한 작업

1. **직접 접속 선택:** 내장 서버 사용 / 기존 서버 직접 접속을 고르는 작은 UI. 기존 인증·원격 repository를 재사용합니다.
   서버를 바꿀 때 서재를 복제하거나 합치지 않습니다. 인증·로그아웃·주소 변경과 내장 서버 수명을 검토한 뒤 구현합니다.
2. **현재 앱 회귀 검증:** 정리본의 Windows 후보에서 시작 → 가져오기/읽기 → 백업·복원 → 종료·재시작.
   기능별 검사 후 한 후보로 묶어 실행하며, 사소한 문서 변경마다 Windows 전체 빌드를 반복하지 않습니다.
3. **자료 이전 확인:** 실제 사용할 기존 백업 형식과 지원 범위를 확인합니다. 거부 중인 모든 과거 형식을 미리 구현하지 않습니다.
4. **배포 점검:** 최종 설치·업데이트에서 profile 보존, 필요한 runtime 설치, 재배포 고지. 준비된 CI/VM에서 확인합니다.
5. **실제 연동:** 필요한 계정·키가 있을 때 사용할 수집기·AI/TTS·네트워크 연결만 확인합니다.

물리적 다른 기기 검증은 이번 범위에서 제외합니다. 앱 내부 Tailscale 자동 설정은 아직 구현된 것으로 표시하지 않으며,
필요 시 네트워크 접속 편의 기능으로 별도 판단합니다. 두 서버 동기화를 그 선행 조건으로 만들지 않습니다.

## 검증 결과

- 공통 sync 전체, 주석/독서 위치, 서버 인증 경계, 백업·복원, 가져오기 기준 revision, reader-state 복원, 내장 서버 UI를 묶은 **19개 파일·90개 검사 통과**.
- 별도 가져오기·페이지 재사용·삭제 검사 묶음 **41개 통과**. 여기의 3개 skip은 명시적으로 비활성화된 성능 benchmark이며 기능 검사 통과 수에 포함하지 않음.
- 수정 전 실제 저장 경로에서 실패했던 3개 검사도 최종 정리 코드로 다시 실행해 모두 통과했습니다.
- 웹·서버 타입 검사, 변경 파일 ESLint, 공통 계약/공개 소스 경계, 서버 production build 검증 통과.
- `smoke-embedded-app.mjs`는 복제용 두 작품과 서버를 제거하고 기존 TXT/EPUB/PDF 3권의 읽기·백업 검사를 유지함. 문법/린트 검사 완료, **정리본의 실제 Windows 실행은 미실시**.
- DB migration 파일은 변경하지 않았고 운영 데이터에 대한 정리 명령도 실행하지 않음.

주요 재현·검사 위치:

- `apps/server/test/client-sync-consistency.integration.test.ts`: 실제 PostgreSQL에서 commit 순서 역전, 위치 저장 실패/중복/동시 삭제, 다른 작품의 메모 변경 차단.
- `apps/server/src/routes/sync/sync-contract-matrix.test.ts`: 기존 v1/v2 클라이언트 사건 계약.
- `apps/server/src/services/import-page-reuse.integration.test.ts`: append·원본·표지·GC·백업 복원·영구 삭제.
- `apps/server/src/services/import-expected-base.integration.test.ts`: 동시 교체 차단과 현재 원본만 담는 백업.

이 결과는 확인한 경로의 회귀 근거이며 전체 제품의 무결함 보장이 아닙니다. 직접 서버 선택 UI와 Windows 후보 검증을 완료했다고 표시하지 않습니다.
