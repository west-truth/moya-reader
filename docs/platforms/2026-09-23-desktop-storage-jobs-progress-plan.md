# 데스크톱 대용량 저장·작업 복구와 공통 진행률 구현 계획

작성일: 2026-09-23. 검토 기준: `f5613f3` / 제품 코드 `8fdef61`.
상태: **계획 작성 완료, 아래 기능은 구현 전**.
상위 문서: [데스크톱 공개 릴리즈 계획](2026-09-23-desktop-release-plan.md).

## 1. 이번 범위와 사용자 결정

- 데스크톱의 파일 기반 보관, 대용량 가져오기·합치기·내보내기·백업/복원을 완성한다.
- 다운로드 중 최소화·창 닫기·절전·재시작의 동작을 정하고, 중단된 작업을 안전하게 이어간다.
- **웹과 데스크톱 공통으로**, 파일 업로드/가져오기와 외부 소스 다운로드에 작은 원형 진행률을 표시한다. 숫자는 원 중앙에 배치한다.
- `전능의 뇌를 얻었다` 연결 문제는 사용자가 ByeDPI를 켜서 해결한 것으로 기록한다. 이를 계속 미해결 앱 결함으로 취급하지 않는다. 다만 권 단위 다운로드 문제는 별도로 확인한다.
- 화면을 가리는 진행 창을 추가하지 않는다. 작품 카드·회차 행에서 상태를 확인하고, 기존 작품 읽기·탐색을 계속할 수 있어야 한다.
- 모든 PC의 최초 오프라인 실행, 종료 후 상주 서비스, 전체 데이터베이스 교체는 이번 범위가 아니다.

## 3. 공통 진행률 UX

### 배치와 조작

- 기본 원 지름은 약 32px, 중앙 숫자는 10~11px의 고정 폭 숫자로 시작해 실제 화면에서 조정한다. 예: **63%**.
- 작품 카드는 기존 상태 표시 자리, 회차 목록은 기존 작업 표시 자리를 사용한다. 작은 표지·텍스트 목록에도 동일한 컴포넌트를 쓴다.
- 주변에는 `업로드 중`, `받는 중`, `저장 중`처럼 짧은 단계만 표시한다. 퍼센트를 텍스트와 원에 중복 표시하지 않는다.
- 총량을 모르는 단계는 숫자 없이 회전 표시한다. 기다린 시간으로 가짜 퍼센트를 만들지 않는다.
- 원을 누르면 기존 작업 상세를 연다. 취소는 상세 또는 기존 작업 메뉴에서 제공해 진행률을 확인하다 실수로 취소하지 않게 한다. 버튼 영역은 최소 44px를 확보한다.
- 다운로드 중에도 이미 저장된 작품은 읽을 수 있다. 새 작품/회차는 읽을 수 있는 상태가 된 뒤 열리며, 일괄 작업 전체가 끝날 때까지 기존 작품을 잠그지 않는다.
- 오류는 같은 자리에 재시도 표시와 짧은 사유를 제공한다. 긴 오류문은 상세로 보낸다.
- 밝은/어두운 테마의 기존 색 토큰을 쓰고, 감소된 모션 설정·키보드·스크린리더를 지원한다. 진행률 숫자는 회전하지 않는다.

### 퍼센트의 의미

**현재 단계의 진행률**을 표시한다. 전체 소요 시간을 알 수 없으므로 전송 90%, 저장 10% 같은 임의 가중치는 사용하지 않는다.

| 작업 단계             | 계산 기준                                                                      | 총량을 모를 때                    |
| --------------------- | ------------------------------------------------------------------------------ | --------------------------------- |
| 파일 읽기/해시        | 읽은 바이트 / 원본 크기                                                        | 준비 중                           |
| 서버 업로드           | 서버가 확인한 청크 바이트 / 전체 바이트. 재시도한 청크는 중복 가산하지 않는다. | 업로드 중                         |
| 단일 파일 다운로드    | 확인 가능한 전체 길이에 대한 받은 바이트. 압축 전후 길이가 다르면 섞지 않는다. | 받는 중                           |
| 이미지 회차 다운로드  | 저장까지 끝난 이미지 / 확정된 이미지 수                                        | 이미지 목록을 얻기 전에는 준비 중 |
| 원본 검사·저장·합치기 | 알려진 처리 바이트 또는 항목 수                                                | 확인 중 / 저장 중                 |
| 최종 메타데이터 반영  | 별도 단계, 시간 추정 없음                                                      | 저장 중                           |

이미지 진행률의 상세에는 `12/28장`을 보여 계산 기준을 알 수 있게 한다. 여러 회차를 받는 경우 카드에는 현재 회차 진행률, 상세에는 완료 회차 수를 표시한다. 크기가 다른 회차들의 퍼센트를 단순 평균하지 않는다.

전송 완료는 작업 완료가 아니다. 업로드가 끝나면 곧바로 다음 단계 표시로 전환하고, 저장/서재 반영 성공 후에만 최종 완료로 처리한다. 한 단계 안에서는 역행하지 않되 재시작·재시도·단계 변경을 숨기기 위해 이전 숫자를 붙잡아 두지 않는다.

진행 정보에는 작업 ID, 단계, 단위, 완료량/전체량, 실행 세대·순서를 포함해 취소된 이전 실행의 이벤트가 현재 UI를 덮지 않게 한다. 이벤트를 매 바이트마다 보내지 않고 묶어서 전달한다. 기존 서버 상태 조회 주기를 재사용하고, 진행률 변경마다 디스크 journal을 쓰지는 않는다.

## 4. 파일 기반 저장과 대용량 처리

### 데이터 구조와 가져오기

1. 데스크톱 capability에서 파일 repository를 선택한다. 일반 웹의 IndexedDB, self-host의 기존 서버 repository는 유지한다.
2. 원본·이미지의 바이너리는 `MoyaData` 아래에 보관하고, 메타데이터에는 상대 경로에 대응하는 불투명 asset ID를 저장한다. 외부 확장에 임의 파일 경로 접근을 주지 않는다.
3. 네이티브 파일 선택/드롭에서 받은 파일은 권한이 확인된 핸들로 읽는다. 대용량 파일을 WebView로 통째로 보내지 않는다. `openSource/readRange`를 읽기 기준으로 재사용한다.
4. 파일 쓰기 → 크기/해시 검증 → 메타데이터 활성화 순서로 처리한다. 기존 `saveImportedNovel` 등 repository 밖의 Blob 쓰기와 삭제 경로도 함께 연결한다.
5. Node 파일 시스템과 IndexedDB 사이에는 단일 트랜잭션이 없으므로 `staging → verified → awaiting_activation → committed` 기록으로 복구한다. 중간에 꺼져도 기존 활성 revision을 유지한다.
6. 삭제·취소 정리는 해당 작업이 기록한 파일에만 적용한다. 디렉터리를 훑어 다른 작업의 임시 파일을 지우는 일반 orphan 정리는 추가하지 않는다.

서버의 ZIP 부분 읽기·스트리밍 해시·ZIP64·검증 helper를 분리해 재사용한다. PostgreSQL에 의존하는 서버 가져오기 서비스를 데스크톱에 그대로 넣거나 별도 서버 전체를 동봉하지 않는다. 이미지 디코딩도 동시 처리 수를 제한해 파일을 디스크에 쓴다는 이유만으로 RAM 문제가 해결됐다고 간주하지 않는다.

### 권 단위 외부 소스

- 실제 실패 기록에서 바이트/이미지 수, 제한 초과, 타임아웃, 디스크 부족, 네트워크 차단을 구분한다. 가능하면 사용자가 언급한 권 단위 회차로 확인하되, 특정 실사이트 응답을 CI 필수 조건으로 두지 않는다.
- 이미지 한 장씩 제한된 동시성으로 받고 검증 후 파일에 저장한다. CBZ 생성·합치기·가져오기에도 파일 참조를 넘긴다. 전체 asset Map이나 최종 CBZ Blob으로 다시 모으지 않는다.
- 파일 기반 소스 경로의 첫 목표는 **회차 합계 1GiB**로 제안한다. 현재 이미지 2,048장/장당 20MiB와 텍스트 제한은 유지한다. 이 수치는 구현 후 메모리·디스크 확인을 통과한 경로에만 적용하며, 구현 중 근거와 함께 확정한다.
- 같은 기능을 사용하는 self-host도 공통 경로·계약을 맞춘다. 기존 메모리 기반 브라우저 fallback은 기존 제한을 유지한다. 계약/실행기 한쪽만 수정해 허용량이 어긋나지 않게 한다.
- 긴 작업은 다운로드 시작/상태/취소를 분리한다. UI HTTP 요청 하나를 오래 붙들고 있지 않는다. 개별 네트워크 요청 제한, 무진행 감지, 전체 작업 상한을 구분하며 전체 제한을 무조건 없애지 않는다.
- 서버 파일 처리 경로가 이미 있는 경우 그것을 연결하고, 데스크톱용 범용 작업 프레임워크를 별도로 만들지 않는다. 기존 큐의 순서·소스별 동시성·사용자 취소 규칙을 유지한다.

로컬 EPUB/ZIP/CBZ는 기존 서버 정책에 맞춰 **입력 4GiB / 압축 해제 합계 8GiB 목표**로 한다. 형식별 검증, ZIP 경로 이탈, 항목 수, 실제 해제 크기, 손상 검사는 유지한다. TXT 등 다른 형식에 이 한도를 무조건 적용하지 않는다.

### 기존 자료 이전

- 새 다운로드부터 파일 보관을 사용하고, 기존 IndexedDB 자료를 읽을 수 있는 호환 경로를 남긴다.
- 파일 백업이 가능해진 뒤 기존 자료 이전을 제공한다. 시작 시 전량 이전을 강제해 앱 사용을 막지 않는다.
- 작품 단위로 복사·검증 후 참조를 바꾼다. 성공이 확인되기 전에 원래 Blob을 지우지 않는다. journal로 재실행 시 이어가며, 공간 부족 시 이전 중단 후 기존 자료를 계속 읽는다.
- 동일 작품의 가져오기/합치기/삭제와 충돌하지 않도록 기존 revision 검사를 재사용한다. 파일 IO 동안 IndexedDB 트랜잭션을 열린 채로 유지하지 않는다.
- 이전 완료 자료의 삭제는 활성 참조와 진행 중 백업 사용 여부를 확인한 뒤 수행한다. 읽기 기록·책 ID·회차 ID를 변경하지 않는다.

## 5. 백업·복원·내보내기

- `exportBackup(): Blob`만으로 처리하지 않고 네이티브 파일 저장 경로를 추가한다. 기존 브라우저 API는 fallback으로 유지한다.
- 기존 로컬 manifest의 의미를 유지하고 파일 asset 참조가 필요한 부분만 명시적으로 버전 관리한다. 기존 백업 읽기를 유지한다. 서버 백업과 포맷이 같다고 가정하거나 상호 복원을 약속하지 않는다.
- ZIP64와 스트리밍 해시 검증을 재사용한다. 256MiB/500항목, 합본 500MiB의 **전체 Blob 처리 때문에 생긴 제한**을 파일 경로에서 해소한다.
- 무제한 해제를 허용하지 않는다. 서버 백업의 100,000항목/비압축 256GiB/개별 객체 5GiB 상한을 파일 경로 안전 상한의 기준으로 삼되, JSON·manifest는 별도의 작은 제한과 유효성 검사를 유지한다. 이는 최대 규모의 실제 실행을 검증했다는 뜻이 아니다.
- 백업 시작 시 메타데이터 snapshot과 참조 자산을 고정한다. 백업 중 읽기·새 다운로드가 가능하되, 참조 중인 자산이 정리되지 않게 한다.
- 목적지에 `.partial` 파일로 쓰고 성공 후 최종 이름으로 바꾼다. 기존 백업을 미리 덮어쓰지 않는다. 임시 파일과 목적지가 다른 볼륨이면 필요한 복사 공간도 계산한다.
- 복원은 먼저 검증·staging하고, 작품별로 반영한다. 기존 skip/replace/copy 정책을 유지한다. 부분 반영 후 실패하면 완료/미완료 작품을 기록해 재개할 수 있게 하며, 전체 원자적 복원이라고 표시하지 않는다.
- 키·쿠키·프록시 인증정보는 일반 백업에 자동 포함하지 않고, 복원만으로 확장 코드를 자동 설치/실행하지 않는다.
- 데이터·임시·저장 대상 볼륨의 실제 여유 공간을 확인한다. 검사는 다른 프로세스의 쓰기를 막지 못하므로 실제 ENOSPC도 처리한다. 이번에 앱 강제 할당량을 추가하지 않는다.

## 6. 최소화·종료·절전·재실행

| 상황                               | 목표 동작                                                                                                  |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 데스크톱 최소화                    | 작업을 계속하고 UI를 다시 열면 최신 상태를 표시한다.                                                       |
| 작업 없는 창 닫기                  | 지금처럼 앱 종료.                                                                                          |
| 작업 중 창 닫기                    | `백그라운드로 계속` / `중단 후 종료` / `돌아가기`. 백그라운드는 트레이로 숨기며 앱 프로세스는 살아 있다.   |
| 트레이                             | 앱 열기, 작업 상태, 종료 정도만 제공한다. 별도 서비스·자동 부팅 실행은 추가하지 않는다.                    |
| PC 절전                            | 진행할 수 없다는 전제. 복귀 후 연결 상태를 확인하고 중단 작업을 복구한다.                                  |
| 앱 강제 종료·재시작                | 기록된 작업을 복원해 `이어받기`를 제공한다. 중복 회차 생성 없이 완료된 파일을 재사용한다.                  |
| 웹에서 서버 업로드 완료 후 탭 종료 | 이미 서버에 접수된 작업은 서버가 계속 처리하고 재접속 시 상태를 복원한다.                                  |
| 웹 업로드 도중 탭 종료             | 브라우저가 닫힌 뒤 전송을 보장하지 않는다. 기존 청크 재개를 이용하고 필요하면 같은 파일 재선택을 요청한다. |
| 서버 없는 일반 웹                  | 브라우저 생명주기 제약을 유지한다. 데스크톱 트레이와 같은 종료 후 동작을 약속하지 않는다.                  |

네이티브 host가 다운로드/파일 작업 상태를 소유하고 UI는 조회·표시한다. 다만 현재 메타데이터 저장은 WebView의 IndexedDB에 있으므로 **host의 파일 처리 완료만으로 서재 등록 완료라고 판단하지 않는다**. 숨겨진 WebView가 이벤트 기반 활성화를 완료하는지 Windows에서 확인한다. WebView가 종료된 경우 `awaiting_activation`으로 남기고 다음 실행에서 반영한다.

재개 기록은 완료 이미지·파일, 원본 식별자, 소스/연결 세대, 대상 작품 revision을 포함한다. 소스 업데이트나 로그인이 바뀌면 기존 조각을 무조건 붙이지 않는다. 개별 파일의 바이트 이어받기는 Range/ETag 검증이 가능한 경우에만 사용하고, 그 외에는 중단된 한 파일을 다시 받는다. 전체 권을 처음부터 다시 받는 일을 줄이는 것이 우선이다.

사용자가 취소한 작업은 자동 재개하지 않는다. 중단 후 종료와 취소를 구분한다. 원본 이동·삭제, 보안 저장소 잠금, 인증 만료는 필요한 재선택/로그인을 짧게 안내한다. 절전 복귀 시 전체 소스를 동시에 재요청하지 않는다.

## 7. 구현 순서와 완료 기준

각 단계에서 코드·필요한 검증·진행 기록을 함께 커밋한다. 아래 순서의 작은 변경으로 진행하며 전체 Windows EXE 빌드를 매 커밋마다 돌리지 않는다.

| 단계                  | 구현 단위                                                                    | 완료 기준과 필요한 검증                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| A. 공통 진행 UI       | 기존 ImportTaskView 확장, 공통 원형 표시, 업로드/기존 진행 정보 연결         | 실제 완료량·미정 총량·단계 전환 projection 검사. 모바일 작은 표지와 PC 회차 행에서 넘침/중복 표시 확인.                       |
| B. 데스크톱 파일 기반 | 파일 선택/저장, asset adapter, staging/journal, 읽기·삭제 연결               | 큰 EPUB/CBZ의 가져오기→읽기→삭제, 취소/공간 부족 시 기존 작품 유지. 메모리가 입력 크기만큼 증가하는 전체 Blob 경로 제거 확인. |
| C. 권 단위 소스 처리  | 공통 다운로드 상세 진행, 디스크 staging, 가져오기/합치기 연계, 작업 상태 API | 256MiB를 넘는 대표 회차를 내려받아 읽기. 중간 실패 후 완료 이미지를 재사용. 재실행/중복 요청 시 같은 회차 중복 생성 방지.     |
| D. 백업과 기존 자료   | 파일 백업·복원·합본 내보내기, 기존 IndexedDB 자료의 선택적 이전              | 기존 제한을 넘는 백업 1건 round-trip, 손상/중단 복원에서 기존 자료 유지, 이전 중단 후 재개. 원본·표지·읽기 기록 확인.         |
| E. 생명주기           | 트레이·닫기 선택, 최소화 계속 처리, 절전/재시작 복구                         | Windows 배포물에서 최소화 중 최종 서재 반영, 닫기/종료/재시작, 절전 복귀를 대표 작업으로 확인.                                |

A는 기존 정보로 바로 시작하되 외부 소스의 상세 퍼센트는 C까지 연결해야 완료다. B에서 복구 기록과 job 상태를 먼저 만들고 E에서 재사용한다. D의 이전 기능은 스트리밍 백업 이후에 제공한다.

자원 비교는 대표 파일 한두 개로 최대 RSS, 소요 시간, 임시 디스크 최고 사용량을 기록한다. 디스크 방식이라고 무조건 더 빠르다고 주장하지 않는다. 각 변경 관련 타입 검사·집중 테스트와 대표 UI/Windows 확인만 수행하고, 전체 플랫폼 테스트·모든 확장 실사이트 검사를 새 필수 CI로 추가하지 않는다.

### 다음 착수 항목

1. A의 진행률 계약과 공통 원형 컴포넌트.
2. B의 파일 IO/asset 저장 최소 경로 및 작업 기록.
3. C의 실제 권 단위 실패 경로 확인과 스트리밍 연결.

한 단계가 끝날 때마다 이 문서에 구현 상태, 검증 범위, 남은 제약을 갱신한다. **이 문서 작성 시점에는 A~E 모두 미착수**다.
