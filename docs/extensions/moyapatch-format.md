# `.moyaext` format and installation foundation

Status: shared format/installer and Hosted API/UI implemented; native execution packaging remains (2026-09-12).

`packages/extension-contracts/package-manifest.ts` defines package v1 separately from the existing integer extension
API v1. Initial packages may describe source/enrichment contributions only. Reserved Moya IDs, foreign contribution
namespaces, native execution, unsupported permissions and ambiguous network origins are rejected. Runtime activation
must additionally check the actual host capabilities; a valid manifest alone does not grant execution.

`src/extensions/packages/package-archive.ts` reads a ZIP without executing its content. Required entries are
`manifest.json`, `integrity.json`, `dist/main.js` and `LICENSE`; optional entries are notices, bounded raster assets and
`signatures/publisher.json`. Entry paths, Unix type, duplicates/case collisions, encryption and declared/actual extracted
sizes are checked. The archive/expanded/code/metadata limits are 10 MiB/30 MiB/5 MiB/64 KiB, with at most 256 entries.

Integrity is the exact canonical UTF-8 representation generated by `canonicalIntegrity`: schema version 1 and a sorted
array of `{path, sha256, size}` for all payload entries, including the manifest and excluding integrity/signature files.
No unlisted payload can be accepted. Optional ECDSA P-256/SHA-256 signatures cover the integrity text prefixed with
`moya.extension.package/integrity/v1\n`. Public keys use SPKI/base64; signatures use WebCrypto's 64-byte raw form.
The publisher fingerprint is SHA-256 of SPKI. A valid self-signature identifies a key, not a trusted publisher.

`package-builder.ts` creates and verifies a package from a manifest, JS bundle, license, optional notices/assets and
optional signing key. The source SDK and repository developer CLI now provide JS/TS folder check/run/pack.
See [source development](source-development.md). Unsigned builds fix ZIP timestamps for stable digests.

`PackageInstaller` requires a host preparation callback. Inspect never executes guest code; install revalidates the
archive and approved digest, checks the reviewed revision, prepares the runtime, then atomically switches active versions.
Same digest is a no-op; different bytes for the same version are rejected. Downgrade and publisher changes require explicit
review. Removal keeps a revision tombstone and publisher pin to fence stale installs and prevent silent trust reset.
Rollback retains the preceding archive/manifest/settings. No Library record, source link or downloaded chapter is deleted.

`IndexedDbPackageInstallStore` uses a separate host-owned `moya.extension-packages.v1` database and readwrite CAS
transaction for records and archive Blobs. This reuses the existing local-first storage boundary instead of adding a second
desktop SQL/file installer. Guest code has no IndexedDB access. Hosted implements the same port with PostgreSQL.
Application backup does not automatically include this separate database.

Hosted now has `PostgresPackageInstallStore` and migration 0046, scoped by the host's owner ID. The same atomic CAS
commits active/previous archive bytes and metadata/settings in one statement. Inventory reads exclude archives and
settings; the runtime catalog loads and verifies changed active versions only. Neither installed code nor package
secrets are added to ordinary reader settings, synchronization or library backups. The existing self-host account is
the owner of the shared library; no user ID will be accepted from package metadata or request JSON.

Generation cancellation and the source registry adapter are connected to the authenticated Hosted API and installation
UI. Windows device installation now shares the installer and source adapter with a bundled native runtime.
Non-secret source storage is separately scoped and commits without changing installation revisions. Hosted migration
0047 and extension IndexedDB v2 preserve installed archives. Source authentication, package settings migration and
installed Windows/WebView2 validation remain.
See [installation and runtime guidance](source-development.md).

Validation: 32 focused tests cover the contract, hashes/signatures, archive boundaries, persistence, install/update failure,
concurrent approval, tombstones, rollback, downgrade/publisher review and cancellation. No full application install E2E is
claimed. See [source development and installation](source-development.md) for the current contract.
